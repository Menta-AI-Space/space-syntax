> ⚠️ **2026-08-26 이후 이 문서의 「저평가」는 제품 결론이 아니다.**
> 제품은 **B(뜰 자리 — 같은 계층 대비 초과상승 확률)** 단일 결론으로 간다. 저평가 계산은
> 유지하되 갭 지표는 **뜰 자리 모델의 입력 feature**로만 쓴다(반증 불가 + 감정평가법상

> 「뜰 자리(오를 확률)」로 읽는다. 화면에 "싸다"로 나가면 안 되고 "오를 확률이 높다"로
> 나가야 한다. 내부 계산·통제 방법을 설명하는 대목은 그대로 유효하다.

| 개별 매물 임대료 | 공공 API 없음 (네이버부동산은 약관상 크롤링 불가) | D4 상권단위 ㎡당 임대료 + **사용자가 임대료 직접 입력** → 적정성 판정 |

## 2. 기능별 상세 설계

### F1. 클릭 → 입지 스코어 (MVP 1) — 실현성 ◎

사용자가 도로/건물 클릭 → 종합점수 + 세부점수 + LLM 설명.

| 세부점수 | 계산 변수 | 소스 | 비고 |
|---|---|---|---|
| Integration Score | integration 값의 **반경 내 백분위** (상위 n%) | D1 (자체) | 절대값 대신 백분위·로컬 랭크로 표기 |
| Choice Score | choice 백분위 | D1 (자체) | |
| Local Accessibility | 반경 400/800/1500m 3-scale 재계산 | D1 (자체) | radius 파라미터만 3개로 |
| Corner/Visibility | 그래프 노드 차수(교차로 여부), 고Choice 세그먼트 접면 | D1 (자체) | degree ≥ 3 = 코너 |
| Transit Score | 최근접 지하철역/정류장 거리, 500m 내 정류장 수 | D8, D9 | 파일데이터 1회 적재 |
| Competition Score | 반경 내 동일 중분류 업종 점포수 / 전체 | D2 (보유) | 이미 있음 |
| Demand Score | 집계구 인구 + 종사자수 + 가구수 (반경 가중합) | D5 | **신규 연동 필요 — 최우선** |
| Rent Context | 해당 상권 ㎡당 임대료·공실률 분위 | D4 | 상권 단위 해상도 한계 명시 |

종합점수 = 가중합 (가중치는 F2 업종 프로파일에 따라 변경).

### F2. 업종 적합도 매칭 (MVP 3) — 실현성 ◎

업종별 가중치 프로파일(룰 기반 매트릭스) — F1 변수 재사용을 기본으로 하되, **단순히 가중치만 바꾸는 수준으로 구현하면 안 된다.**

업종이 바뀌면 다음 항목이 함께 바뀌어야 한다.

1. 누구를 경쟁사로 볼지
2. 어느 범위까지 분석할지
3. 어떤 시간대를 볼지
4. 어떤 고객을 핵심 수요로 볼지
5. 어떤 공공 매출 업종을 연결할지
6. 어떤 입지 지표를 중요하게 볼지
7. Cannibalization을 어떤 방식으로 계산할지
8. 화면에 무엇을 보여줄지

초기 업종별 방향성:

| 업종 | Integration | Choice | 유동/수요 | 경쟁 | 특수 변수 |
|---|---|---|---|---|---|
| 편의점 | 중 | **상** | 주거+직장 인구 | 동일업종 거리 | 24h 배후 (D5+D7) |
| 카페 | **상** | 중 | 종사자·학생 | 밀집 허용 | 사무실·대학 근접 (D5, D11) |
| 병의원 | 중 | 하 | 배후 인구 안정성 | 동일 진료과 | 역 근접 (D8) |
| 학원 | 중 | 하 | 학령인구·가구 | 학원 밀집 = 양의 신호 | 학교 근접 (D11, D5 연령대) |
| 음식점 | 상 | 중 | 저녁·주말 체류 | 업종다양성 | 서울=시간대 생활인구 (D7) |

출력: "적합: 편의점·테이크아웃 카페 / 부적합: 목적형 음식점" + 근거.

#### F2.1 Industry Analysis Profile 요구사항

시스템은 모든 업종에 동일한 경쟁사 분석 모델을 적용해서는 안 된다. 각 업종은 별도의 `IndustryAnalysisProfile`로 정의하고, 프로파일에 따라 데이터 수집, 경쟁사 분류, 점수 계산, 지도 레이어, 화면 KPI, AI 해석이 달라져야 한다.

프로파일은 코드에 하드코딩하지 않고 DB 또는 설정 파일에서 버전 관리한다. 초기 구현은 JSON 파일 기반으로 시작할 수 있다.

```text
industry-profiles/
├── food/
│   ├── salad-poke.json
│   ├── korean-restaurant.json
│   ├── cafe.json
│   └── delivery-only.json
├── medical/
│   ├── dermatology.json
│   ├── dental.json
│   └── internal-medicine.json
├── beauty/
│   ├── hair-salon.json
│   └── nail-salon.json
└── education/
    ├── english-academy.json
    └── math-academy.json
```

필수 스키마:

```ts
interface IndustryAnalysisProfile {
  id: string;
  name: string;
  parentCategory: string;

  customerSegments: CustomerSegment[];
  consumptionMissions: ConsumptionMission[];

  catchmentModel: CatchmentModel;
  timeSlots: IndustryTimeSlot[];

  directCompetitors: CompetitorRule[];
  secondaryCompetitors: CompetitorRule[];
  indirectCompetitors: CompetitorRule[];
  channelCompetitors: CompetitorRule[];

  demandFeatures: WeightedFeature[];
  competitionFeatures: WeightedFeature[];
  siteFeatures: WeightedFeature[];
  salesFeatures: WeightedFeature[];
  cannibalizationFeatures: WeightedFeature[];

  publicSalesMappings: PublicIndustryMapping[];
  outputModules: IndustryOutputModule[];

  thresholds: {
    direct: number;
    secondary: number;
    indirect: number;
  };

  version: string;
  effectiveFrom: string;
}
```

샐러드·포케 예시:

```json
{
  "id": "salad-poke",
  "name": "샐러드·포케",
  "parentCategory": "food",
  "catchmentModel": {
    "walkMinutes": [5, 10],
    "deliveryMinutes": [10, 15, 20]
  },
  "timeSlots": ["weekday_lunch", "weekday_dinner"],
  "competitorCategories": {
    "direct": ["salad", "poke"],
    "secondary": ["sandwich", "healthy_lunchbox", "diet_food"],
    "indirect": ["premium_gimbap", "rice_bowl", "convenience_meal"],
    "channel": ["delivery_healthy_meal", "convenience_store_meal"]
  },
  "siteWeights": {
    "choice": 0.2,
    "integration": 0.15,
    "transit": 0.15,
    "workerDemand": 0.2,
    "deliveryCoverage": 0.2,
    "visibility": 0.1
  }
}
```

#### F2.2 경쟁사 정의

산업분류 코드가 같다는 이유만으로 같은 강도의 경쟁사로 보면 안 된다. 경쟁 관계는 선택 업종의 고객, 가격대, 방문 목적, 채널, 시간대에 따라 달라진다.

| 선택 업종 | 직접 경쟁 | 준직접 경쟁 | 간접/채널 경쟁 | 핵심 구분 기준 |
|---|---|---|---|---|
| 샐러드·포케 | 샐러드, 포케 전문점 | 샌드위치, 건강 도시락, 다이어트식 | 김밥, 덮밥, 편의점 도시락, 배달권역 건강식 | 건강식/1인식/배달 가능 여부 |
| 카페 | 유사 가격대·이용 목적 카페 | 베이커리 카페, 디저트점 | 편의점 커피, 패스트푸드 커피 | 테이크아웃형·체류형·디저트형·저가형 |
| 병원 | 동일 진료과 | 유사 증상 치료 진료과 | 다른 진료과는 원칙적으로 비경쟁 | 의료진, 진료시간, 장비, 주차 |
| 미용실 | 동일 가격대·고객층 미용실 | 1인숍, 바버숍, 헤어 전문점 | 홈케어/저가 체인 등 | 예약, 디자이너 수, 가격, 최근 리뷰 |

#### F2.3 업종별 상권 범위 모델

모든 업종에 `500m / 1km` 원형 반경만 적용하면 분석이 왜곡된다. 업종 프로파일은 다음 권역 모델 중 하나 이상을 선택한다.

| 권역 모델 | 기준 | 적용 예 |
|---|---|---|
| Walk Catchment | 보행 이동시간 | 편의점, 카페, 음식점, 약국, 생활서비스 |
| Drive Catchment | 차량 이동시간 | 대형마트, 병원, 자동차 서비스, 대형 학원, 목적형 소매점 |
| Transit Catchment | 대중교통 이동시간·환승 | 전문병원, 대형 학원, 문화시설, 목적형 상업시설 |
| Delivery Catchment | 도로망 이동시간·배달 가능 시간 | 음식점, 카페, 배달 전문점, 장보기 서비스 |
| Residential Catchment | 주거지·학교·직장 등 수요 발생지와 생활권 관계 | 학원, 어린이 시설, 세탁소, 미용실, 동네 병원 |

초기 분석권역 기준:

| 업종 | 핵심 분석권역 |
|---|---|
| 편의점 | 도보 3~5분 |
| 카페 | 도보 5~10분 |
| 점심 음식점 | 도보 5~8분 |
| 배달 음식점 | 차량·배달 10~20분 |
| 미용실 | 도보·차량 10~20분 |
| 피부과 | 대중교통 20~40분 |
| 학원 | 주거지·학교 기반 10~30분 |
| 대형마트 | 차량 15~30분 |

#### F2.4 핵심 시간대

경쟁점은 단순히 가까운 점포가 아니라 핵심 영업시간과 수요 시간이 겹치는 점포여야 한다.

| 업종 | 핵심 시간대 |
|---|---|
| 샐러드·포케 | 평일 점심, 평일 저녁 |
| 카페 | 출근 시간, 점심 이후, 주말 오후 |
| 술집 | 평일 저녁, 금·토 심야 |
| 병원 | 평일 주간, 토요일 오전 |
| 미용실 | 평일 저녁, 주말 |
| 학원 | 방과 후, 저녁 |
| 편의점 | 심야 포함 전 시간대 |

#### F2.5 경쟁사 분류 엔진

각 점포의 경쟁 관계는 단순 업종 코드가 아니라 판매 메뉴/서비스, 가격대, 고객 연령, 방문 목적, 이용 시간대, 홀·포장·배달 채널, 점포 규모, 브랜드 유형을 함께 사용해 계산한다.

```text
CompetitorSimilarity =
  w1 * CategorySimilarity
+ w2 * ProductSimilarity
+ w3 * CustomerSimilarity
+ w4 * PriceSimilarity
+ w5 * MissionSimilarity
+ w6 * ChannelSimilarity
+ w7 * TimeOverlap
```

기본 분류 기준:

| 점수 | 분류 |
|---:|---|
| 0.80 이상 | 직접 경쟁 |
| 0.60 이상 0.80 미만 | 준직접 경쟁 |
| 0.35 이상 0.60 미만 | 간접 경쟁 |
| 0.35 미만 | 비경쟁 또는 참고 점포 |

임계값은 업종 프로파일별로 변경 가능해야 한다.

#### F2.6 경쟁 영향력 모델

경쟁점의 영향력은 업종별 가중치를 적용해 계산한다.

```text
CompetitorImpact_i =
  Similarity_i
* CatchmentOverlap_i
* OperatingTimeOverlap_i
* CompetitorStrength_i
* MarketPressure_i
```

`CompetitorStrength` 구성요소는 업종별로 다르다.

| 업종 | 경쟁력 변수 |
|---|---|
| 음식점 | 메뉴 유사도, 가격대, 리뷰 수, 최근 리뷰 증가, 배달 여부, 최소 주문금액, 배달비, 영업시간, 브랜드 인지도 |
| 카페 | 테이크아웃/체류형, 좌석 수, 브랜드 인지도, 가격대, 디저트 구성, 영업시간, 리뷰 증가, 대로변·코너 입지 |
| 병원 | 진료과, 의료진 수, 전문의 여부, 진료시간, 야간·주말 진료, 주차, 의료장비, 개원 기간, 접근 생활권 인구 |
| 미용실 | 디자이너 수, 예약 가능 여부, 시술 종류, 시술 가격, 최근 리뷰 증가, 영업시간, 고객 성별·연령대, 브랜드 여부 |
| 학원 | 과목, 대상 학년, 인근 학교, 통학 접근성, 수강 규모, 수업 시간, 브랜드, 셔틀 운영 여부 |

업종별 필수 변수가 없는 경우 해당 변수는 0으로 처리하지 않고, 가용 변수의 가중치를 재분배한다.

#### F2.7 공공 추정매출 매핑

공공 상권 데이터의 공식 업종과 실제 소비 카테고리가 일치하지 않을 수 있으므로, 각 업종 프로파일은 공공 업종 코드와의 매핑 규칙을 가져야 한다.

샐러드·포케 예시:

| 공식 업종 | 초기 관련 가중치 |
|---|---:|
| 기타 간이 음식점업 | 0.35 |
| 서양식 음식점업 | 0.20 |
| 한식 음식점업 | 0.10 |
| 김밥 및 간이 음식점 | 0.15 |
| 비알코올 음료점업 | 0.05 |
| 기타 건강식 관련 업종 | 0.15 |

카페 예시:

| 공식 업종 | 초기 관련 가중치 |
|---|---:|
| 커피·음료점업 | 0.70 |
| 제과점업 | 0.15 |
| 기타 간이 음식점업 | 0.10 |
| 아이스크림·디저트 | 0.05 |

공공 매출은 업종별 가중 합산을 통해 `RelevantMarketSalesProxy`를 생성한다. 이 값은 개별 브랜드나 점포의 실제 매출로 표현하지 않는다.

#### F2.8 업종별 Site Score

`SiteScore`는 모든 업종에서 같은 방식으로 계산하지 않는다. 각 가중치는 업종 프로파일에서 관리한다.

| 업종 | 예시 계산식 |
|---|---|
| 음식점 | `0.25 Choice + 0.20 Integration + 0.15 Visibility + 0.15 Transit + 0.15 Walkability + 0.10 Parking` |
| 배달 전문 음식점 | `0.10 Choice + 0.10 Integration + 0.05 Visibility + 0.15 RiderAccess + 0.20 RoadTravelTime + 0.15 RentEfficiency + 0.25 DeliveryCoverage` |
| 병원 | `0.10 Choice + 0.15 Transit + 0.20 Parking + 0.20 TargetPopulation + 0.15 Accessibility + 0.20 MedicalCompetition` |
| 편의점 | `0.25 PedestrianFlow + 0.20 CornerVisibility + 0.20 ResidentialDemand + 0.15 LateNightDemand + 0.10 Connectivity + 0.10 CompetitionGap` |

#### F2.9 업종별 Cannibalization Risk

Cannibalization Risk의 구성도 업종별로 달라져야 하며, 업종 프로파일에 정의된 중첩 변수만 사용한다.

| 업종 | 중첩 변수 |
|---|---|
| 음식점 | 도보권 중첩, 배달권 중첩, 메뉴 중첩, 가격대 중첩, 시간대 중첩 |
| 카페 | 도보권 중첩, 체류형·테이크아웃형 중첩, 고객층 중첩, 출근·오후·주말 수요 중첩 |
| 병원 | 진료권 중첩, 동일 진료과, 환자 연령대, 대중교통 접근권 중첩, 의료진 및 진료시간 차이 |
| 미용실 | 생활권 중첩, 가격대 중첩, 고객 성별·연령대, 예약 가능 시간, 디자이너 유형 |

#### F2.10 업종별 결과 화면과 AI 해석

업종 선택에 따라 상세 분석 탭과 KPI가 달라져야 한다. 관련 없는 KPI는 0으로 표시하지 않고 화면에서 숨긴다.

| 업종 | 표시 KPI/탭 |
|---|---|
| 음식점 | 점심·저녁 수요, 배달 수요, 메뉴 경쟁, 가격대 경쟁, 배달권역, 동일 소비 목적 경쟁점 |
| 카페 | 테이크아웃 수요, 체류 수요, 좌석 공급, 오전·오후 수요, 저가·프리미엄 경쟁 |
| 병원 | 진료권 인구, 연령대별 환자 잠재수요, 동일 진료과 공급, 야간·주말 진료 공백, 주차 및 대중교통 |
| 미용실 | 생활권 인구, 핵심 여성 연령층, 예약 경쟁, 가격대 분포, 디자이너 공급 |

AI 해석 프롬프트에는 선택 업종, `IndustryAnalysisProfile`, 적용된 권역 모델, 직접·준직접·간접 경쟁사, 핵심 수요 변수, 적용 가중치, 누락 데이터, 데이터 신뢰도를 전달해야 한다. AI는 해당 업종과 관련 없는 일반 조언을 생성해서는 안 된다. 예: 병원 분석에 메뉴 차별화를 제안하거나, 배달 전문점에 간판 가시성을 핵심 위험으로 단정하면 안 된다.

#### F2.11 관리자 기능

관리자는 다음 항목을 수정할 수 있어야 한다.

- 업종 프로파일 추가·수정

- 공식 업종 코드 매핑
- 직접·간접 경쟁 임계값
- 분석권역과 이동시간
- 시간대 가중치
- 고객층 가중치
- Site Score 가중치
- Competition Score 가중치
- Cannibalization 가중치
- 화면 노출 KPI

변경된 프로파일에는 버전 번호와 적용일을 저장한다.

#### F2.12 기능 수용 기준

| AC-IND-04 | 배달 전문점 분석에서는 도보 Choice보다 배달권역과 차량 이동시간에 더 높은 가중치를 적용해야 한다. |

#### F2.13 업종·사용자 유형별 적응형 분석 화면

시스템은 모든 업종과 모든 사용자에게 동일한 분석 화면을 제공해서는 안 된다. 공통 UI 구조는 유지하되, 다음 조건에 따라 화면 구성을 동적으로 바꾼다.

- 업종 / 세부 업종
- 브랜드
- 운영 형태
- 사용자 유형
- 분석 목적
- 보유 데이터 수준

동적으로 변경되는 대상은 핵심 KPI, 분석 탭, 지도 레이어, 경쟁사 분류, 분석 권역, 시간대, 결과 문구, 추천 전략, 경고 항목, 보고서 구성이다.

##### 사용자 유형별 기본 화면

| 사용자 유형 | 주요 의사결정 질문 | 우선 표시 화면 | 화면 복잡도/깊이 |
|---|---|---|---|
| 예비 창업자 | 이 위치에 열어도 되는가, 주요 고객/시간대/경쟁/임대료 부담은 어떤가, 다른 후보지보다 나은가 | 출점 적합도, 주요 고객, 핵심 수요 시간대, 경쟁 강도, 임대료 부담, 위험 요인, 후보지 비교, 추천 운영 전략 | 기본 결과와 자연어 설명 우선. 복잡한 통계는 상세보기로 제공 |
| 프랜차이즈 본사 | 신규점이 기존점을 잠식하는가, 신규 시장을 확보하는가, 브랜드 미커버 지역은 어디인가 | 점포망 지도, 기존점 목록, 신규 후보지, Cannibalization Risk, 신규 커버리지, 중복 시장, 배달권역 전후 비교, 후보지 일괄 비교, 출점 심의 보고서 | 점포망/브랜드 전체 영향, 내부 데이터 업로드, 승인·보류 상태 관리 우선 |
| 상업용 부동산 중개사 | 이 매물에는 어떤 업종이 적합한가, 임차인에게 어떤 근거를 제시할 수 있는가 | 매물 기본정보, 추천 업종, 업종별 적합도, 주변 수요, 경쟁환경, 교통·도로 접근성, 임대조건, 매물 제안서 생성 | 임차인 설득 근거와 매물 장점 비교 우선 |
| 건물주 | 공실에 어떤 업종을 유치해야 하는가, 장기 유지 가능성과 임대료 수준은 적절한가 | 추천 업종 순위, 업종별 수요, 공급 부족 업종, 장기 공실 위험, 건물 입지 장단점, 임대료 경쟁력, 유치 대상 브랜드 유형 | 공실 해소와 장기 안정성 우선 |

##### 공통 화면 영역과 동적 화면 영역

모든 업종에서 다음 공통 구조는 유지한다.

- 상단 입력 영역: 업종 선택, 브랜드 선택, 주소 검색, 분석 목적, 분석권역, 기존점 선택, 분석 실행
- 공통 요약 영역: 종합 출점 적합도, 핵심 기회, 핵심 위험, 데이터 신뢰도, 분석 기준, 추천 또는 보류 의견
- 공통 기능: 관심 목록 추가, 후보지 비교, 보고서 생성, AI 질문, 데이터 출처 보기

업종과 사용자 유형에 따라 다음 요소는 동적으로 변경한다.

- 요약 카드
- 상세 탭
- 지도 레이어
- 차트
- 경쟁사 목록
- 분석 범위
- 비교 지표
- 추천 문구

##### Industry UI Profile

각 업종은 분석 규칙뿐 아니라 화면 구성 규칙을 가져야 한다. `IndustryUIProfile`은 프론트엔드 코드에 직접 하드코딩하지 않고 DB, JSON 설정 파일, 관리자 페이지, 버전 관리 가능한 구성 파일 중 하나로 관리한다.

```ts
interface IndustryUIProfile {
  industryId: string;
  userType: UserType;

  summaryKpis: KPIConfig[];
  primaryTabs: TabConfig[];
  secondaryTabs: TabConfig[];
  mapLayers: MapLayerConfig[];
  competitorViews: CompetitorViewConfig[];
  charts: ChartConfig[];
  alerts: AlertRule[];
  recommendations: RecommendationRule[];
  reportSections: ReportSectionConfig[];
}
```

업종이 추가되더라도 화면 전체를 새로 개발하지 않고 `IndustryAnalysisProfile`과 `IndustryUIProfile` 설정을 통해 확장할 수 있어야 한다.

##### 업종별 화면 구성

| 업종 | 핵심 KPI | 주요 탭 | 기본 지도 레이어 | 화면 원칙/핵심 질문 |

##### 요약 화면 요구사항

요약 화면은 선택 업종의 핵심 의사결정 질문에 직접 답하는 한 줄 결론을 제공한다.

예: `평일 점심 수요와 배달 신규 커버리지가 강하지만 기존 신촌점과의 중첩 위험이 높습니다.`

요약에는 다음을 포함한다.

- 핵심 기회: 최대 3개
- 핵심 위험: 최대 3개
- 추천 전략: 업종별로 다르게 표시
  - 음식점: 점심 회전율, 포장, 배달
  - 카페: 테이크아웃 또는 체류형 선택
  - 병원: 진료시간, 주차, 진료 공백
  - 학원: 대상 학년과 통학권
  - 미용실: 가격대와 고객층

##### 후보지 비교 화면

| 병원 | 진료권 인구, 동일 진료과 공급, 의료 공백, 대중교통, 차량 접근, 주차 |

##### 데이터 부족 화면 처리

업종 특화 데이터가 없는 경우 임의 값을 생성하지 않는다. 다음 중 하나로 처리한다.

- 해당 KPI 숨김
- 데이터 없음 표시
- 대체지표 표시
- 데이터 신뢰도 하향
- 분석 범위 제한 설명

예: `미용실 예약 경쟁 데이터는 현재 제공되지 않아 점포 수와 상권 매출을 기반으로 경쟁 강도를 계산했습니다.`

##### MVP 범위

MVP 포함 업종군은 음식점, 카페·제과, 미용, 병·의원, 학원, 편의점·생활소매다.

MVP 포함 사용자 유형은 예비 창업자와 프랜차이즈 본사다.

MVP 포함 화면은 업종별 요약 화면, 업종별 KPI, 업종별 지도 레이어, 업종별 경쟁사 화면, 후보지 비교, 프랜차이즈 기존점 영향 화면이다.

MVP 이후 범위는 건물주 모드, 중개사 모드, 업종 자동 추천, 화면 커스터마이징, 브랜드별 자체 UI 프로파일, 화이트라벨 보고서다.

##### 핵심 제품 원칙

업종별 분석이란 단순히 점수 가중치만 다르게 적용하는 것이 아니다. 업종이 변경되면 핵심 질문, 분석권역, 경쟁사 정의, 수요 변수, KPI, 지도 레이어, 상세 탭, 위험 경고, 추천 전략, 비교 기준, 보고서 구성이 함께 달라져야 한다.

사용자 유형이 변경되면 동일한 분석 결과도 다른 우선순위와 깊이로 제공해야 한다. 창업자에게는 단일 점포의 성공 가능성을 중심으로 제공하고, 프랜차이즈 본사에는 브랜드 전체 점포망의 확장성과 잠식 위험을 중심으로 제공한다.

### F3. 후보지 2~5개 비교 (MVP 2) — 실현성 ◎

F1을 후보지마다 실행 → 표로 랭킹. 신규 데이터 불필요, `POST /api/compare` 라우트 + 프론트 비교 테이블만.

### F4. 저평가 거리 탐지 — 실현성 ○

로직: `구조값(Integration/Choice) 백분위 高` ∧ `점포밀도(D2) 低 또는 증가중` ∧ `상권 임대료(D4) 인근 대비 低`.
`undervaluation.py` 뼈대 보유. 한계: 임대료가 상권 단위라 "거리(street)" 해상도가 아님 → **"저평가 후보 구간"** 정도로 표현 수위 조절.

### F5. 임대료 적정성 — 실현성 ○

절대 예측 ✕, **사용자 입력 임대료 vs 벤치마크 밴드** 비교:
- D4 상권 ㎡당 임대료 × 면적 = 기준 밴드
- D4 층별효용비율로 층 보정, D10 건축물대장으로 층/용도 확인
- D3 RTMS 상업용 매매가로 자산가치 맥락 추가
- 출력: "이 상권 기준 밴드 260~310만원, 입력 320만원 → 다소 높음. 단 코너+고Choice 입지라 카페·편의점이면 수용 가능."

### F6. 공실 리스크 진단 — 실현성 ○ (추정 모델)

| 요인 | 소스 |
|---|---|
| 낮은 Integration/Choice 백분위 | D1 |
| 상권 공실률 (분기) | D4 |
| 지하/상층부 여부, 건물 노후도 | D10 |
| 반경 내 앵커(대형마트·역·대학) 부재 | D8, D11, D13 |
| 임대료 > 상권 밴드 | D4 + 입력 |
| 서울: 개폐업률·상권변화지표 | D6 |

출력은 점수가 아닌 등급(낮음/중간/높음) + 요인 목록. 법적 리스크 회피를 위해 "추정"임을 항상 명시.

### F7. Before/After 시뮬레이션 — 실현성 ◎ (외부데이터 불필요)

그래프에 가상 엣지(신설 보행로/출구) 추가·삭제 → Integration/Choice 재계산 → 전후 비교. 순수 자체 엔진 기능. B2B(개발사·지자체) 차별화 포인트지만 MVP 후순위.

### F8. 외부 데이터 레이어 (지도 오버레이)

D5 인구/종사자 히트맵, D2 점포 밀도, D8/D9 교통, D11 학교, (서울) D6 매출·유동인구. F1~F6이 쓰는 데이터를 시각화만 하는 것이므로 데이터 적재 후 프론트 작업.

### F9. PDF 리포트 (MVP 4) — 실현성 ◎

F1+F2+F3 결과 + 지도 캡처 → 서버사이드 PDF (weasyprint/playwright). 과금 포인트.

### F10. LLM 자연어 설명 — 실현성 ◎ (즉시 가능, 네 직감이 맞음)

F1의 구조화된 변수(백분위, 랭크, 경쟁, 수요, 임대 맥락)를 Claude API에 넣어 설명 생성.
핵심: **LLM은 계산하지 않고 번역만 한다** — 숫자는 전부 백엔드가 계산, LLM은 "이 도로는 반경 1km 내 Integration 상위 8%로 주변에서 자연스럽게 도달하기 쉬운 길입니다. 다만 통과 교통량(Choice)은 중간이라 목적형보다 근린형 업종에 유리합니다" 식 해석만. 환각 위험 최소화 + 지금 데이터만으로 바로 구현 가능.

## 3. 신규 연동 우선순위 (데이터 작업 순서)

1. **D5 SGIS** (인구·종사자) — Demand Score의 뼈대, 전국 커버, 없으면 F1이 반쪽 → 최우선
2. **D8/D9 지하철·버스** — 파일데이터 1회 적재로 끝, 가성비 최고
3. **D4 부동산원 임대동향** — F5/F6의 핵심, 상권경계 매핑 작업 필요
4. **D6 서울 상권분석서비스** — 서울 한정이지만 매출·유동인구·개폐업 = 최고 가치 데이터
5. **D10 건축물대장** — 클릭한 건물의 층/용도 (F5/F6 보정)
6. **D11 NEIS** — 학원/학교 (F2 업종 매칭용)
7. **D7 생활인구** — 시간대 분석 고도화 (후순위)

## 3.5 확장 기능 (2차 로드맵 — 전부 공개데이터/자체 엔진으로 가능)

| 기능 | 내용 | 데이터 | 실현성 / 단서 |
|---|---|---|---|
| E1. 도보 도달권 (아이소크론) | 클릭 지점에서 도보 5/10/15분 도달 영역 + 영역 내 인구·가구(D5)·경쟁점(D2). 속도 파라미터만 바꾸면 자전거/배달권 | 자체 그래프 + D5 + D2 | ◎ 외부 의존 없음. **E2·최적출점의 기반 인프라 — 확장기능 중 최우선** |
| E2. 잠식(cannibalization) 분석 | ① 경쟁 잠식: 도달권 내 동일업종 거리가중 점수 ② 자기 잠식: 기존 매장과 후보지의 도달권 겹침 % (D2 상호명 필드로 브랜드 매칭 가능) | D2 + E1 재사용 | ◎ 단, 매출 감소 예측은 불가 → "잠식 위험 점수"로 표현 |
| E3. 뜨는 거리 추적 | 상가업소 분기 스냅샷 적재 → 업종 비중 변화율로 성장 신호 감지. 과거 분기 파일 백필 가능 | D2 (분기 CSV) | ○ 시계열 노이즈 → 절대값 대신 상대 비중 변화 사용. **스냅샷 적재는 지금부터 시작** |
| E4. 대화형 입지 상담 | 채팅으로 조건 입력 → LLM이 스캐너·진단·잠식 API를 도구 호출해 답변 | 자체 API + Claude API | ◎ MVP 1~3 API 완성 후. 근거가 전부 자체 계산값이라 환각 위험 낮음 |
| E5. 최적 출점 스캐너 | 조건에 맞는 자리를 지역 전체에서 역방향 검색 (F1 점수의 일괄 계산) | 기존 재사용 | ◎ 비교 기능의 상위 호환 — 킬러 기능 후보 |
| E6. 유사 입지 찾기 | 거리별 특징 벡터 코사인 유사도 — "제2의 성수동 찾기". F4와 결합 시 "구조 같고 임대료 절반인 거리" | 자체 계산값 | ◎ |
| E7. 관심 지역 모니터링 | 등록 지역의 개폐업·임대료·공실률 분기 변화 알림 | 기존 재조회 | ◎ 구독 수익 모델 |
| E8. 매물 붙여넣기 진단 / 내 가게 진단 | 매물 텍스트를 LLM이 파싱해 자동 진단 / 운영 중 가게 역진단 | 사용자 입력 + 기존 재사용 | ◎ |

확장 기능 구현 순서: **E1 → E2 → E5 → E6 → E3(적재는 즉시 시작) → E4 → E7/E8**
