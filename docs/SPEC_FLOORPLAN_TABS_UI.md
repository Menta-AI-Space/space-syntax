# 도면 분석을 탭형 제품 화면으로 낸다 — 인식 화면 + 7탭 결과

**상태: 소유자 구술(2026-08-24)을 옮긴 초안. 구현 착수 전이고 데이터·계산의 대부분이 아직
없다.** 아래 「데이터 실사」 표가 그 사실을 항목별로 갈라 둔 것이다. 지금 저장소에 서 있는
도면 분석은 **업로드 → 벽 편집 → VGA 한 판 → 목/보이는 범위 히트맵** 한 줄기뿐이고
(`FloorplanAnalyzer.tsx` 472줄, `floorplan_vga.py` 460줄), 이 문서가 적는 7탭 중 **어느 탭도
지금 코드로는 채워지지 않는다.** 없는 것을 "곧 된다"고 읽지 말 것.

이 문서는 `docs/SPEC_LAND_VALUE_TABS_UI.md`의 형식을 따른다. 두 문서는 **같은 제품 원칙**을
공유한다 — 지표가 아니라 질문으로 탭을 나누고, AI는 입구가 아니라 후속 설명 창구다.

---

## Problem Statement

지금 도면 분석 화면(`AppShell`의 「도면 분석」 탭 → `FloorplanAnalyzer`)이 사용자에게 내는
결과는 **숫자 다섯 개와 색칠한 격자 하나**다: 살펴본 칸 수, 평균 목, 가장 좋은 목, 평균
보이는 칸, 도면 반영률. 그리고 규칙 기반 설명 네 문장
(`rule_based_floorplan_explanation`).

그래서 두 가지가 안 된다:

1. **사용자가 무엇을 해야 하는지 모른다.** "가장 목이 좋은 자리는 (312, 480) 부근입니다"는
   좌표다. 설계를 어디서 어떻게 고치라는 말이 아니다.
2. **Depthmap과 구별되지 않는다.** 지금 화면이 하는 일은 depthmapX가 20년째 하던 일의
   부분집합이다. 제품이 되려면 **문제를 찾아 주고 개선안을 도면 위에 표시**해야 한다.

**이 화면이 답해야 할 질문은 "Integration이 얼마인가"가 아니라 "이 도면의 무엇이
문제인가"다.**

## Solution

### 1. 전체 레이아웃

```
┌──────────────────────────────────────────────────────────────┐
│ 헤더: 프로젝트명 │ 파일명 │ 층 선택 │ 분석 상태 │ 보고서 다운로드 │
├──────────────────────────────────────────────────────────────┤
│ 탭 바: 발견된문제 · 사용자동선 · 공간효율 · 안전·접근성 ·      │
│        설계개선 · A/B비교 · 보고서                             │
├────────────────────────────────────┬─────────────────────────┤
│                                    │                         │
│         도면 (70%)                 │   분석·설명 패널 (30%)   │
│   — 탭이 바뀌어도 계속 유지된다     │   — 탭마다 내용이 바뀐다  │
│                                    │                         │
├────────────────────────────────────┴─────────────────────────┤
│ 하단 고정: AI에게 물어보기  [                            ] [↑] │
└──────────────────────────────────────────────────────────────┘
```

**핵심 원칙: 모든 탭에서 도면은 계속 유지되고, 선택한 탭에 따라 도면 위 표시와 오른쪽
설명만 바뀐다.** 아래 「결정 2」로 따로 뽑았다.

### 2. 0단계 — 도면 업로드·인식 화면 (분석 전)

탭 바에 들어가기 전 단계다. 분석을 시작하기 전에 **AI가 무엇을 어떻게 읽었는지 사람이
확인하고 고치는 자리**다.

| 영역 | 내용 |
| --- | --- |
| 가운데 | DXF 업로드 · 미리보기 · 층 선택 · 축척 확인 |
| 오른쪽 | AI가 인식한 요소 목록 |
| 아래 | 버튼 3개 — 도면 인식 수정 / 공간 용도 설정 / 분석 시작 |

인식 결과 목록(구술한 예시 수치):

| 요소 | 개수 |
| --- | --- |
| 공간 | 17 |
| 벽체 | 46 |
| 문 | 19 |
| 창문 | 11 |
| 주출입구 | 1 |
| 비상구 | 2 |
| 계단 | 2 |
| 엘리베이터 | 1 |
| **인식 실패** | **3** |

인식이 미심쩍은 곳은 **도면 위에 번호로 표시**한다:

1. ① 끊어진 벽체를 출입문으로 판단했을 가능성
2. ② 실명(室名) 없는 공간
3. ③ 축척 자동 확인 실패

⚠️ **이 화면 전체가 지금 코드에 없다.** 현재 추출 결과는 `lines`(벽 선분)과
`openings`(문·창 선분) 두 배열뿐이며, "공간 17개"·"계단 2개"·"주출입구 1개" 같은
**의미 요소를 식별하는 코드가 없다.** 아래 실사 표 참조.

### 3. 최종 탭 7개

| # | 탭 | 답하는 질문 |
| --- | --- | --- |
| 1 | **발견된 문제** (default) | 이 도면의 무엇이 문제인가 |
| 2 | **사용자 동선** | 누가 어디로 어떻게 다니는가 |
| 3 | **공간 효율** | 면적을 잘 쓰고 있는가 |
| 4 | **안전·접근성** | 피난과 접근에 위험이 있는가 |
| 5 | **설계 개선** | 어디를 어떻게 바꾸면 되는가 |
| 6 | **A/B 비교** | 바꾸면 무엇이 좋아지고 무엇이 나빠지는가 |
| 7 | **보고서** | 이걸 어떻게 남기는가 |

**default 탭은 「발견된 문제」다.** 「종합」이나 「개요」가 아니다 — 사용자는 도면의 문제를
찾으러 온다.

## 탭별 내용

### 1. 발견된 문제 (default) — 사실상 메인 대시보드

지표를 먼저 내지 않는다. **중요한 문제부터** 낸다.

도면 위에는 번호 마커가 붙고, 색이 중요도다:

| 색 | 뜻 |
| --- | --- |
| 🔴 빨강 | 즉시 검토 |
| 🟠 주황 | 개선 권장 |
| 🔵 파랑 | 참고 |

문제 목록(구술한 예시 5개):

| # | 문제 | 중요도 |
| --- | --- | --- |
| ① | 방문자 동선과 물류 동선이 충돌한다 | 즉시 검토 |
| ② | 입구에서 안내데스크가 보이지 않는다 | 개선 권장 |
| ③ | 사용하기 어려운 잔여공간이 있다 | 개선 권장 |
| ④ | 비상구 경로가 한 방향에 의존한다 | 즉시 검토 |
| ⑤ | 휠체어 이동 폭 확인이 필요하다 | 참고 |

오른쪽 패널은 **중요도 순 나열**이고, 문제 하나마다 네 칸이 붙는다:

| 칸 | 내용 |
| --- | --- |
| 설명 | 무엇이 문제인지 한 문단 |
| 업무상 영향 | 이 문제가 실제 운영에서 무엇을 뜻하는지 |
| 분석 근거 | 접었다 펴는 영역 — 여기에 Space Syntax 지표가 들어간다 (결정 1) |
| 추천 조치 | 무엇을 하면 되는지 |

버튼 4개: **도면에서 위치 보기 / 개선안 만들기 / 검토 완료 / 담당자 메모**.

문제 ①의 「분석 근거」 예시:

```
동선 중첩 구간          6m
최단경로 집중도         상위 9%
해당 구간 연결 공간     4개
예상 병목               1곳
```

### 2. 사용자 동선

상단 입력:

| 입력 | 값 |
| --- | --- |
| 사용자 유형 | 방문자 · 직원 · 관리자 · 물류 직원 · 교통약자 · **직접 추가** |
| 출발지 | 공간 선택 |
| 목적지 | 공간 선택 |
| 비교 대상 | 다른 사용자 유형 |

도면 위 표시:

- 실선 = 방문자 동선, 점선 = 물류 동선
- 중첩 구간 강조
- 병목 지점 번호
- 방향 전환 화살표
- 이동이 집중되는 공간 색칠

오른쪽 패널:

```
이동거리              42m
방향 전환             4회
예상 이동시간         (분·초)
동선 중첩             6m
통과하는 보안구역     1곳
길 찾기 어려운 지점   2곳
```

그 아래 AI 설명 한 문단.

**Space Syntax의 Choice·Integration·Depth는 판단 근거로만 작게 표시한다.** 이 탭의
주인공은 "42m·4회·6m"이지 "Choice 상위 9%"가 아니다.

### 3. 공간 효율

도면을 **유형별로 색칠**한다: 실제 사용 / 이동 / 공용 / 설비 / 잔여 / 미지정.
공간을 클릭하면 면적과 사용 가능성이 뜬다.

오른쪽 패널:

```
전체 면적        520㎡
전용 면적        369㎡
공용 면적        151㎡
이동공간 비율     23%
비효율 공간       18㎡
```

+ 발견된 문제 + 개선 가능성.

버튼: **공간별 면적표 / 비효율 공간만 보기 / 개선안 생성 / 엑셀 다운로드**.

### 4. 안전·접근성

⚠️ **이 탭은 법규 최종 판정이 아니라 설계 위험 사전점검이다.** 성격을 잘못 읽히면 제품이
감당 못 할 책임을 진다.

내부 메뉴 둘:

**(a) 피난·안전**

- 주 피난경로 / 대체 피난경로
- 출구까지 거리
- 막다른 복도
- 병목 가능 구간
- 비상구가 보이지 않는 공간
- 출구 집중 구간

**(b) 교통약자 접근성**

- 휠체어 이동 경로
- 출입문·복도 유효폭
- 회전 공간
- 엘리베이터 접근성
- 장애인 화장실까지 거리
- 단차 의심 구간

**반드시 화면에 넣을 문구**(고정 문구, 삭제 금지):

> 자동 사전검토 결과이며 최종 법규 적합성은 건축사 및 관련 전문가의 확인이 필요합니다.

### 5. 설계 개선

**Depthmap과 가장 확실히 갈리는 탭이다.** 지표를 보여주는 도구는 많지만 "여기를 이렇게
바꾸라"고 도면 위에 그려 주는 도구는 없다.

개선안마다 두 칸: **변경 내용 / 예상 효과**.

| 개선안 | 변경 내용 | 예상 효과 |
| --- | --- | --- |
| 1. 서비스 동선 분리 | 물류 동선을 별도 경로로 분리 | 중첩 6m → 0m · 혼잡 감소 · 전용공간 노출 제거 · 물류 이동거리 +3m |
| 2. 안내데스크 이동 | 입구 시야 안으로 이동 | 가시성 증가 · 방향 전환 4회 → 2회 · 길 찾기 취약 2곳 → 0곳 |

개선안 1은 **좋아지는 것과 나빠지는 것을 함께 적는다**(물류 +3m). 한쪽만 적으면 개선안이
아니라 광고다.

도면 위 표시: 현재 상태 · 추천 위치 · 변경 예상 범위 · 전후 동선.

버튼 5개: **개선안 적용 미리보기 / 다른 대안 만들기 / A/B 비교로 보내기 / 개선안 무시 /
설계자 의견 입력**.

**MVP에서 자동 수정까지는 안 하더라도, 어디를 어떻게 바꾸면 되는지는 도면에 표시해야
한다.** 표시가 없으면 이 탭은 글머리표 목록에 불과하다.

### 6. A/B 비교

```
┌─────────────┬─────────────┬─────────────┐
│   A안 도면   │   B안 도면   │  비교 설명   │
└─────────────┴─────────────┴─────────────┘
```

좁은 화면에서는 토글: **A안 / B안 / 변경 부분만 보기**.

| 항목 | A안 | B안 | 변화 |
| --- | --- | --- | --- |
| 전용면적 비율 | 71% | 74% | +3%p |
| 방문자 이동거리 | 42m | 37m | −11.9% |
| 동선 중첩 | 6m | 0m | 해소 |
| 길 찾기 취약 지점 | 2곳 | 0곳 | 개선 |
| 피난 취약 지점 | 1곳 | 1곳 | **변화 없음** |
| 가시 사각지대 | 3곳 | 2곳 | 1곳 감소 |

AI 종합설명은 **B안에 남은 문제를 짚는다** — 예: 휴게실의 대체 피난경로가 여전히 없다.

### 7. 보고서

목차 10개:

1. 프로젝트 개요
2. 도면 인식 결과
3. 주요 문제 요약
4. 사용자별 동선
5. 공간 효율
6. 안전·접근성 사전검토
7. 가시성·공간구조
8. 개선 제안
9. A/B 대안 비교
10. 분석 조건과 한계

출력 형식: **PDF · PPT · Excel 면적표 · 문제가 표시된 도면 이미지 · 검토 의견서**.

### 하단 고정 AI 채팅

모든 탭 아래에 붙어 있다. 예시 질문 7개:

1. 이 도면에서 가장 큰 문제는 뭐야?
2. 방문자가 화장실 찾기 어렵지 않을까?
3. 물류 동선이 방문자랑 겹치는 데 어디야?
4. 회의실 위치를 바꾸면 뭐가 좋아져?
5. 휠체어로 이동할 때 불편한 구간 알려줘
6. 비상시 대피가 가장 어려운 공간은?
7. 이 도면에서 낭비되는 공간이 얼마나 돼?

**요구**: AI가 답하면서 **해당 위치를 도면에서 자동 강조**해야 한다. 말로만 답하면
사용자가 좌표를 눈으로 찾아야 하고, 그건 지금 `rule_based_floorplan_explanation`이
"(312, 480) 부근"이라고 답하는 것과 같은 실패다.

## 별도 결정

### 결정 1. Space Syntax 지표를 독립 탭으로 만들지 않는다

Integration · Choice · VGA는 **전용 탭을 갖지 않는다.** 각 문제의 「분석 근거 보기」 안에
접어 넣는다.

이유: **사용자는 지표를 보러 오는 게 아니라 도면의 문제를 찾고 설계를 개선하러 온다.**
지표는 판정의 근거이지 판정 자체가 아니다.

이것은 `docs/SPEC_LAND_VALUE_TABS_UI.md`가 내린 것과 **같은 원칙**이다 — 그 문서는
"Space Syntax를 **전용 탭으로 만들지 않는다** — 공간 데이터 묶음의 하나로 둔다"고 적고
Integration·Choice를 「입지·도시계획」 탭 안에 넣었다. 토지 쪽과 도면 쪽이 같은 원칙을
쓴다는 사실을 양쪽 문서에 남긴다(상호 참조).

⚠️ **이 결정은 지금 화면을 뒤집는다.** 현재 `FloorplanAnalyzer`의 결과 카드는 제목이
"건물 안에서의 목"이고 토글이 「목」/「한눈에 보이는 범위」다 — 즉 **지표가 화면의
주인공**이다. 새 구조에서 그 두 값은 근거 영역으로 내려간다.

### 결정 2. 탭이 바뀌어도 도면은 유지된다

**도면이 화면의 주인공이고 패널이 주석이다.** 탭 전환은 도면을 갈아 끼우는 것이 아니라
도면 위 레이어와 오른쪽 설명을 바꾸는 것이다.

구현상 뜻: 도면 캔버스는 탭 컴포넌트 **바깥**에 서고, 탭은 캔버스에 그릴 오버레이 목록과
패널 내용을 내려보낸다. 지금 `FloorplanAnalyzer`는 캔버스 하나에 `useEffect` 한 개가
모든 그리기를 하므로(벽·개구부·격자·제외칸), **오버레이 레이어 개념부터 새로 세워야
한다.**

### 결정 3. A/B 비교를 단일 점수로 끝내지 않는다

**"B안 87점" 같은 단일 점수를 내지 않는다.** 무엇이 좋아지고 **무엇이 나빠졌는지 함께**
보여준다.

이유는 위 비교표 자체다 — B안은 이동거리·중첩·길찾기에서 이겼지만 **피난 취약 지점은
그대로**다. 87점은 그 사실을 지운다. 설계 결정은 트레이드오프이고, 트레이드오프를 한
숫자로 접으면 사용자는 무엇을 포기했는지 모르는 채로 채택한다.

같은 이유로 개선안 1의 「물류 +3m」도 지우지 않는다.

### 2026-09-30 진전 — 실무 도면을 견디게 (레이어 선택·틈 메우기·XREF 감지)

여태 시험한 건 전부 우리가 만든 합성 도면이었고 레이어 이름이 `WALL`/`DOOR`로 깔끔했다.
실제 사무소 도면을 흉내 내 보니 **에러 없이 조용히 틀린 결과를 내는** 자리가 셋 있었다.

| 증상 | 실측 | 조치 |
| --- | --- | --- |
| 레이어 이름이 `구조체`·`칸막이` | 이름 매칭 실패 → **모든 레이어를 벽으로 합치고 문을 통째로 버림**. 반영률 100% → **31%** | ① 선 총길이가 가장 긴 레이어 **하나만** 벽으로 짚는다(전부 합치지 않는다) ② 문 레이어를 이름으로 찾았으면 벽을 짐작했더라도 살린다 ③ **레이어 목록을 화면에 내고 사람이 고치게** 한다 |
| 외벽이 한 군데 끊김 | 분석 칸 1,415 → 1,118로 줄었는데 **반영률은 100%로 표시** (반영률은 실내 대비라 실내가 줄면 같이 줄어 문제를 가린다) | ① 벽 끝점이 1.5칸 안에서 어긋나면 이어 붙이고 몇 군데인지 알린다 ② 벽이 감싼 범위 대비 실내가 75% 미만이면 **"외곽선이 닫혀 있지 않은 것 같습니다"** 경고 |
| XREF(외부 참조) | 벽이 다른 파일에 있어 빈 도면이 옴 | 감지해서 **"BIND한 뒤 다시 저장해 주세요"**라고 말한다. 데이터가 없으므로 복구는 불가능 |

치수·해치·중심선 레이어는 이름으로 걸러낸다(`dim`·`치수`·`hatch`·`center`…). 그래서 벽
후보가 하나도 안 남는 경우에도 **실패로 끝내지 않고** 레이어 목록과 도면 범위를 돌려줘
사람이 "이게 벽이다"라고 지정할 수 있게 했다.

**API**: `POST /api/floorplan/extract`가 `wall_layers`·`opening_layers`(쉼표 구분)를 받는다.
파일을 서버에 보관하지 않으므로 고칠 때마다 다시 올린다 — 남의 건물 설계도를 쌓아 두지
않는 편이 낫다는 판단이다.

**검토 후 버린 것**: 레이어 이름 사전을 계속 늘리기(사무소마다 달라 끝이 없다 → 통계
추측 + 사람 확인으로 갈음). 끊긴 벽을 크게 메우기(문까지 막혀 방이 밀폐된다 → 1.5칸으로
제한하고 나머지는 경고로).

### 2026-09-30 밤 — 실무 도면에서 더 걸릴 자리 셋을 미리 막았다

실제 도면을 흉내 내 더 찔러 보니 **에러 없이 조용히 틀리는** 자리가 셋 더 나왔다.

| 증상 | 왜 생기나 | 조치 |
| --- | --- | --- |
| 호(ARC)·원·곡선 폴리라인(bulge)을 버림 | 합성 도면이 전부 직선이라 LINE·POLYLINE만 읽고 있었다. 실제 도면은 둥근 벽·문 심볼·곡선 통로를 이걸로 그린다 | ezdxf의 `flattening()`·`virtual_entities()`로 편다. **각도 해석을 직접 하지 않는다** — 손으로 회전 방향 규약을 다루다 반원이 뒤집혔다 |
| 평면 전체가 블록(INSERT) 하나 | 모델스페이스에 INSERT만 있고 선이 없어 "선 엔티티를 찾지 못했습니다"로 끝났다. 화면에는 도면이 멀쩡히 보이는데 | INSERT를 펼쳐 원래 레이어대로 다시 분류(중첩 4단계까지, 레이어 `0`은 꽂은 쪽을 따름). **이름으로 알아본 심볼(계단·EV·출입구)은 펼치지 않는다** — 계단 그림의 선이 벽이 되어 방을 막는다 |
| `외벽`은 잡히고 `칸막이`는 안 잡힘 | 이름 규칙에 걸리는 레이어가 하나라도 있으면 나머지는 조용히 버려진다. 내벽이 빠지면 **방이 나뉘지 않아 매장별 표가 통째로 틀린다** | 벽 레이어 길이의 15%를 넘는 다른 선 레이어를 `suspect_wall_layers`로 내고, 화면이 "벽일 수도"라고 표시하며 레이어 목록을 자동으로 펼친다 |

셋 다 합성 몰의 기존 수치(벽 102·문 25)를 흔들지 않는다는 테스트를 함께 고정했다.

크기에만 비례시켰는데, 200×150m 도면은 한 칸이 3.7m라 허용 거리가 **5.5m**가 됐다 —

cm 단위지 미터 단위가 아니다). 고친 뒤 대형 도면의 잘못된 연결 124건이 사라졌고,
20cm 어긋난 벽은 여전히 이어진다.

**돌아간 도면이 새어 나가던 것도 잡았다.** 실제 도면은 대지 방향을 따라 돌아가 있는 일이

100%가 됐고, 정방향 도면은 13에서 이미 최대라 결과가 그대로다(1,991칸). 비스듬한 벽이

### 축척 — 이 화면의 가장 큰 구멍 (2026-09-17 메움)

**2026-09-17**: `$INSUNITS`를 읽어 `meters_per_unit`을 extract 응답에 싣고, analyze 요청이
그 값을 받아 `cell_size_m`·m 좌표를 낸다. 단위 헤더가 없으면(0 = unitless) 경고를 내고
화면의 「도면 가로 길이 m」 입력으로 사용자가 채운다. 아래는 그 전 상태의 기록이다.

**미터가 나오는 항목이 이 문서에 12개 있다**(42m, 6m, 520㎡, 369㎡, 18㎡, 유효폭, 피난거리
…). 지금 파이프라인은 그중 **하나도** 낼 수 없다. 이유는 추출 코드에 있다:

```python
scale = MAX_IMAGE_DIM / max(span_x, span_y)      # MAX_IMAGE_DIM = 1600
...
canvas_width=span_x * scale,
```

즉 DXF의 실제 도면 단위를 **긴 변이 1600px이 되도록 정규화해 버리고, 그 배율을 응답에
돌려주지 않는다.** `$INSUNITS`(DXF 단위 헤더)를 읽지도 않는다. 결과 좌표계는 무차원
픽셀이다.

그래서 **면적·거리·유효폭이 걸린 탭 3·4·6은 축척 복원 없이는 시작할 수 없다.** 고치는 건
어렵지 않다(배율과 단위를 응답에 함께 실으면 된다) — **미결 Q3**에 그 결정을 뒀다.
0단계의 "축척 자동 확인 실패 ③"이 예시 항목이 아니라 **기본 상태**임을 알고 설계해야 한다.

### DXF만 받는 제약이 이 화면 흐름에 뜻하는 것

`docs/ARCHITECTURE_RULES.md`가 정한 대로 `/api/floorplan/extract`는 **DXF만** 받고
사진·스캔은 프론트(`accept=".dxf"`)와 백엔드 양쪽에서 막는다. 이 화면 흐름에는 세 가지
뜻이 있다:

1. **좋은 쪽** — 이 문서가 요구하는 의미 요소 인식(문·계단·용도)은 **래스터에서는
   가망이 없고 벡터에서는 가망이 있다.** 레이어명·블록명·TEXT가 파일 안에 이미 들어 있다.
   지금 코드가 그중 레이어명만 쓰고 있을 뿐이다.
2. **나쁜 쪽** — 사용자가 가진 게 PDF·사진뿐이면 이 제품 전체를 못 쓴다. 0단계 업로드
   화면이 그 사실을 **거절 메시지가 아니라 안내**로 말해야 한다.
3. **위험한 쪽** — 레이어 이름 규칙이 사무소마다 다르다. `_layer_kind`는
   `wall|벽`, `door|glaz|window|wind|문|창` 여섯 needle의 **문자열 포함 검사**다.
   `A-WALL-FULL`은 잡히지만 `구조체`·`칸막이`·`PARTITION`은 못 잡는다. 그러면
   `wall_layer_lines`가 비어 **모든 레이어를 벽으로 삼는 폴백**이 돌고, 그때는
   `opening_lines`를 통째로 버린다(코드 주석: 문이 어느 선인지 알 수 없으므로). 즉
   **레이어 규칙이 어긋난 도면은 문이 하나도 없는 밀폐 도면으로 분석된다.**
   0단계 「도면 인식 수정」이 장식이 아니라 **필수 관문**인 이유다.

### 2026-11-09 — 결과를 두고 되묻는 「도면 상담」 (하단 AI 채팅의 첫 구현, 해커톤 01)

컴포넌트. AI 해석 바로 밑에 붙고, 예시 질문 칩 4개(도면에 있는 카드 종류에 따라 고른다) ·
입력칸 · 말풍선 · 「소리로 듣기」 · 「N번 카드 자리 도면에서 보기」로 이뤄진다.

**어떻게 동작하나**: 라우터는 그대로 stateless다 — 화면이 분석 응답(summary·카드·방·규칙
요약)과 화면에 보이는 AI 해석, 지금까지의 대화(최근 12턴)를 매번 함께 보낸다. 서버는 그
사실을 한 블록으로 만들어 system 다음 첫 user 턴에 싣고, 모델은 **입력에 있는 사실만** 쉬운
말·존댓말·3~5문장으로 답한다(영어·전문 용어 금지, 위치는 카드 번호와 방향으로). 답이 카드
하나에 관한 것이면 끝에 「【카드 N】」을 달게 하고, 서버가 그 표지를 떼어 `card` 번호로 돌려주며
화면은 그 카드 구역을 도면에 칠하고 「발견된 문제」 탭으로 옮겨 도면을 보여 준다 — Q10의
「자연어만으로는 강조할 수 없다」에 대한 답이다(좌표가 아니라 카드 번호라는 구조화된 계약).

화면에 「AI 없이 요약문으로 답했습니다」)으로 돌아간다. 새 분석마다 대화를 비운다(카드 번호가
바뀌므로).

**5초 룰**: `/explain`과 같은 자리다 — 분석 뒤에 따로 부르는 서술이라 분석 예산 밖이고,
`ARCHITECTURE_RULES.md`의 「유일한 예외」(도구 루프)와도 다르다(도구를 안 부르고 한 번 묻는다).

**검토 후 버린 안**: ① `/api/agent/ask` 도구 루프에 도면 도구를 붙이기 — 분석 결과를 세션에
보관하거나 다시 계산해야 해 Q9(저장) 결정을 먼저 요구한다. ② 답을 JSON으로 받기 — 로컬 LLM
전환 때 깨지기 쉬워 끝 표지 한 줄로 했다. ③ 좌표를 돌려받아 칠하기 — 모델이 좌표를 지어낼

어떤 문장을 내는지는 배포 뒤 라이브에서 봐야 한다.**

(`lib/useSpeechInput`, 크롬·엣지, 한국어). 들은 말은 **바로 보내지 않고 입력칸에 넣는다**(잘못 들은 것을
고칠 기회, 특히 「68번」 같은 숫자). 마이크를 켤 때 읽어 주던 답은 멈춘다(스피커 소리를 받아 적는 것 방지).
**말로 고치기(「여기 벽 터 줘」)는 안 만들었다** — AI 답을 좌표 명령으로 바꿔 편집기에 넣는 계약과 좌표
지어내기(Q6) 방지 장치가 필요해 반나절 일이고, 소유자에게 그렇게 말했다. 시연 흐름은 「말로 묻기 → 마우스로
문 내기 → 다시 분석 → 바꾼 것과 비교」.

**남은 것**: 라이브에서 답 품질·시간 실측(예상 10~25초) · 답에 좌표(m)가 섞여 나오면 프롬프트
보강 · 보고서(탭 7)에 대화 내용 넣을지 · 1인 사용량 상한(예선 제출문의 본선 계획 항목) · 말로 고치기.

## 미결 — 답이 나와야 구현에 들어간다

1. **Q1 · 의미 요소 인식을 무엇으로 하나.** 지금은 레이어명 문자열 포함 검사 여섯 개가
   전부다. 선택지: (a) 레이어명 규칙을 넓히고 사용자에게 레이어→의미 매핑을 시킨다
   (0단계 「도면 인식 수정」), (b) BLOCK/INSERT 이름과 TEXT/MTEXT를 읽어 규칙으로
   분류한다, (c) 기하 규칙으로 추론한다(문 = 벽 개구부 + ARC 스윙, 계단 = 등간격 평행선
   다발), (d) 모델. **(b)는 `_entity_segments`가 INSERT·ARC·TEXT를 버리는 것부터 고쳐야
   한다.** 어디까지 갈지 정해야 0단계 화면의 "공간 17 / 계단 2"가 뜻을 갖는다.

2. **Q2 · 「공간」을 어떻게 만드나.** 탭 2·3·4가 전부 "방"을 단위로 말하는데 지금은
   격자 셀뿐이다. 선택지: (a) 벽 선분으로 닫힌 폴리곤을 위상적으로 구성한다,
   (b) 격자에서 연결요소를 잘라 방으로 본다(개구부 때문에 방이 서로 붙는다 —
   `_exterior_mask`가 이미 그 문제와 싸우고 있다), (c) DXF의 HATCH·공간 폴리라인 레이어를
   신뢰한다. **이 답이 없으면 「출발지/목적지 선택」 드롭다운을 채울 수 없다.**

3. **Q3 · 축척을 어떻게 복원하고 어디까지 책임지나.** `$INSUNITS`를 읽을지, 사용자에게
   기준선 두 점을 찍게 할지, 둘 다 할지. 그리고 **축척이 확인되지 않은 도면에서 미터
   표기를 아예 감출지**(권장) 아니면 "축척 미확인" 배지를 달고 낼지. 지금 응답은 배율을
   돌려주지도 않으므로 계약(`FloorplanExtractResponse`)이 바뀐다.

4. **Q4 · 사용자 유형별 동선을 무슨 알고리즘으로 내나.** VGA 가시성 그래프는 **경로
   그래프가 아니다** — 벽 너머로 보이는 칸이 이웃이라 그 위의 최단경로는 벽을 통과한다.
   따로 **보행 그래프**(자유셀 8-이웃 + 개구부 통과)를 세워야 한다. 그러면 격자 하나에
   그래프 둘이고, 5초 예산을 다시 재야 한다(지금 VGA만으로 대형 몰 도면 1.74초,
   `MAX_GRID_CELLS=2200` 제약이 이미 그 때문에 있다). "사용자 유형"의 차이는 무엇으로
   내나 — 출발/목적지 집합만 다른가, 통행 가능 구역이 다른가(보안구역·직원 전용),
   속도·회전 비용이 다른가(교통약자).

5. **Q5 · 유효폭·피난거리를 어느 기준으로 재고 책임 범위를 어디까지 두나.**
   「건축물의 피난·방화구조 등의 기준에 관한 규칙」과 「장애인등편의법」 시행규칙의 어느
   조문을 참조값으로 쓸지, 그 값을 **화면에 조문과 함께 인용할지**, 아니면 조문 없이
   "권장 폭 미달"로만 말할지. 조문을 인용하면 제품이 법규 판정으로 읽히고, 안 하면 근거가
   없다. 탭 4의 고정 문구만으로 이 긴장이 해소되지 않는다. **법무 판단이 필요한 유일한
   미결이다.**

6. **Q6 · 개선안 생성을 규칙으로 하나 모델로 하나.** 규칙이면 "중첩 구간이 Xm 이상이면
   분리 제안" 같은 트리거 표를 사람이 다 적어야 하고, 모델이면 도면 기하를 넣고 좌표를
   받아야 하는데 **LLM이 좌표를 지어낼 위험**이 그대로다(토지 쪽 문서의 "없는 데이터를
   가짜로 채우지 않는다"와 같은 문제). 절충안: 위치는 규칙이 정하고 **문장만 모델이
   쓴다** — 지금 `rule_based_floorplan_explanation`이 이미 그 형태다(`source:"rule"`).

7. **Q7 · A/B의 B안을 사람이 그리나 시스템이 만드나.** 사람이 그리면 지금 벽 편집기를
   확장하면 되고(도면 두 벌 상태 관리), 시스템이 만들면 Q6과 묶인다. 그리고 **비교
   지표를 재려면 B안도 전체 파이프라인을 한 번 더 돌려야 한다** — 5초 룰이 두 배가 된다.
   비교는 비동기로 뺄지, 예산을 나눌지.

8. **Q8 · 보고서를 어디서 렌더하나.** 백엔드(reportlab/python-pptx — 의존성 추가 + 한글
   폰트 + Railway 이미지 크기) vs 프론트(브라우저 인쇄 / canvas → PDF). **PDF·PPT 생성은
   5초 룰의 대상이 아니다** — 분석이 아니라 내려받기다. 그렇다면 `/api/agent/ask`에 이어
   **두 번째 예외**를 만드는 것이고, `docs/ARCHITECTURE_RULES.md`가 "예외는 하나뿐"이라고
   못 박아 두었으므로 그 문서를 함께 고쳐야 한다. 아니면 비동기 작업으로 빼서 예외가
   아니게 만든다.

9. **Q9 · 상태를 어디에 저장하나.** 「검토 완료」·「담당자 메모」·「설계자 의견」·프로젝트명·
   층 목록·A/B 두 안은 전부 **저장이 필요한데 지금 라우터는 stateless·no-DB**다(파일 머리
   주석이 그렇게 못 박고 있다). 세션 로컬로 둘지, 프로젝트 테이블을 만들지. 만들면 이
   기능은 **처음으로 로그인·소유권이 필요한 화면**이 된다.

10. **Q10 · AI 채팅이 도면을 어떻게 보나.** 도구 루프가 도면 컨텍스트를 받으려면
    분석 결과를 세션에 보관하거나 도구가 다시 계산해야 한다(Q9와 묶인다). 그리고
    "답하면서 도면을 강조"하려면 답변에 **요소 id 또는 좌표를 실은 구조화된 계약**이
    필요하다 — 자연어만으로는 강조할 수 없다.

### 2026-11-08 — 반영률이 낮으면 결론 문단이 먼저 밝힌다 (UX 자동 개선)

wtc-mall 샘플(반영률 65%)에서 결론 문단이 「건물 안을 격자 254칸으로 나눠 살펴봤습니다. 목이 가장 좋은 곳은…」으로
도면 전체를 본 듯 읽혔고, 35%가 빠졌다는 말은 1번 카드와 맨 아래 「이렇게 계산했습니다」에만 있었다. 반영률 70% 미만
(1번 카드가 뜨는 같은 문턱)이면 첫 문장 바로 뒤에 「다만 도면 열린 공간의 35%가 벽에 막혀 계산에서 빠졌고, 아래 내용은
이어진 나머지만의 결과입니다 — 1번 카드를 먼저 확인하세요」를 넣는다(카드 kind="excluded"). 버린 안: 반영률이 낮으면
가장 좋은/외진 곳 문장을 아예 빼기 — 남은 부분 결과도 쓸모가 있어 버렸다. 「이어 붙였습니다」 개수도 천 단위 쉼표(2,200군데).

### 2026-11-09 — 「말로 고치기」: 자리를 찍고 말·글로 시키면 도면이 고쳐진다 (1단계)

소유자: 「도면을 수정할 때 사용자가 위치를 마우스로 선택하면, 말 혹은 메시지로 보내서 도면을 수정할 수 있게
— GPT가 이미지 수정하는 것처럼」.

**결정 — 그림이 아니라 편집 명령을 고치게 한다.** GPT는 「어느 벽에 무엇을 할지」만 고르고, 선을 자르고
붙이는 건 코드가 계산한다. 결과가 기존 벽·문 배열 그대로라 「바꾼 것과 비교하기」에 바로 이어진다.

흐름: 편집 도구 다섯 번째 「말로 고치기」 → 도면을 **누르면 점, 끌면 네모** → 입력창(글 + 🎤) →
`POST /api/floorplan/edit-intent` → 미리보기(새로 생기는 것 초록·사라지는 것 빨간 점선) → **적용 / 취소**
→ 적용하면 기존 되돌리기 목록에 쌓인다.

- 서버(`floorplan_edit_intent.py`)는 선택 자리 주변 벽·문만 추려 번호(w1·d1…)·길이·방향·주변 매장 이름과 함께
  GPT(`complete_json`)에 보낸다. GPT는 명령 다섯 개 중에서만 고른다: **문 내기 · 벽 지우기 · 문 막기 · 벽 세우기 ·
  네모 안 벽 모두 지우기**. 애매하면 되물음(question)을 돌려준다.
- 서버가 명령을 검증·계산해 「더할 선 / 지울 선 번호」로 돌려준다. 선택 자리에서 멀리 떨어진 곳은 고치지 않는다.
- GPT가 꺼져 있거나 실패하면 낱말 규칙(문 내/뚫 · 지워/없애/터 · 문 막/닫 · 벽 세워/만들)으로 같은 명령을 만든다.
- 음성은 1탭과 같은 브라우저 음성 입력(`useSpeechInput`) — **크롬 계열만 되고 아이폰 사파리는 버튼이 숨는다.**

**정한 기본값 (소유자 「해」 — 제안한 추천안 그대로)**: 미리보기 뒤 「적용」(바로 적용 안 함 — 잘못 알아들은 게
바로 보이게) · 1단계 명령은 문·벽 계열만(방 합치기·벽 옮기기는 2단계) · 음성은 무료 브라우저 음성부터.

**버린 안**: ① GPT 이미지 모델로 도면 그림을 직접 수정 — 결과가 그림이라 분석이 안 되고(§7 DXF만), 같은 말에도
매번 다르게 그려져 비교 숫자가 흔들린다. ② GPT가 좌표를 직접 내게 하기 — 엉뚱한 자리에 선이 생겨도 막을 길이 없다.
벽 세우기만 좌표를 받고, 그것도 선택 자리 근처로 묶고 가까운 벽 끝에 붙인다. ③ 바로 적용 + 되돌리기 — 음성 오인식이
그대로 도면에 들어간다.

**남은 일(2단계 이후)**: 선택 없이 이름으로 지목(「17번과 18번 매장 사이」), 한 문장 여러 명령, 아이폰 음성(서버
음성 인식 — 유료라 소유자 승인 필요), AI 해석 「고칠 곳과 방법」 카드에 「이대로 고쳐 보기」.

**1단계 결과 (2026-11-09, c23e238 라이브)**: 대형 복합몰 샘플, 17·18번 매장 사이를 한 번 누르고 「17번이랑 18번 매장 사이

**알려진 한계**: 이 모드에선 도면 위 손가락 스크롤을 막아(네모 끌기용) 「도면 크게 보기」 상태에서 도면을 밀어 옮길 수 없다 —
다른 도구로 바꿔 옮긴 뒤 돌아와야 한다. 2단계에서 두 손가락 이동 등으로 푼다.

**2026-11-09 바꿈 — 묻지 않고 바로 적용** (소유자: 「적용할래?라고 물으면 적용을 해 주라」). 위 기본값 「미리보기 뒤 적용」을
뒤집었다. 지시를 보내면 바로 도면에 들어가고, 패널에 「바꿨습니다 + 무엇을 했는지 + 되돌리기」, 도면엔 바뀐 자리를 초록(생김)·
빨간 점선(없어짐)으로 남긴다(다른 자리를 고르거나 되돌리면 사라짐). 입력칸은 그대로 남아 이어서 시킬 수 있다. 응답을 기다리는 사이
도면이 바뀌었으면(되돌리기 등) 지울 선 번호가 어긋나므로 적용하지 않고 「다시 시켜 주세요」. 안내 문장은 과거형(「문을 냈습니다」).
버린 안: 미리보기 확인 단계 유지 — 소유자가 한 번 더 묻는 단계를 원치 않음. 오인식 위험은 바로 옆 되돌리기로 받는다.

**2026-11-09 다시 바꿈 — LLM이 묻고, 말로 답한다** (소유자: 「아니 LLM이 물으라고」 — 바로 위 「바로 적용」은 뜻을 잘못 읽은 것).
지시를 보내면 LLM이 제안 + 「적용할까요?」를 말하고(미리보기 초록·빨간 점선, 소리로 듣기 버튼), 사용자가 같은 칸·마이크로
「응/네/적용해」라고 답하면 적용, 「아니/취소」면 취소, 「아니 2미터로」처럼 내용이 붙으면 직전 지시와 합쳐(`previous_instruction`)
새 제안을 받는다. 답 가르기는 프론트 `confirmIntent`(짧은 예/아니오만 — 애매하면 고쳐 말한 것으로 본다), 「적용」「취소」 버튼도 남겼다.
같이 고친 버그: 「2미터」의 「터」가 「벽 터 줘」(지우기)로 잡혔다. 로컬 확인(규칙 경로): 「여기 문 내줘」→3m 제안 →「아니 2미터로」→2m 제안
→「응」→ 문 77→78 →「이 문 막아 줘」→「아니」→ 취소.

**2026-11-09 라이브 시험(소유자와 같이 봄, 7d79a49)**: 17·18번 매장 경계를 누르고 「17번이랑 18번 매장 사이 벽 뚫어서 통로 내줘」 →
GPT가 **거꾸로** 「기존 문 d2를 메우는 것」을 제안(안쪽 번호까지 노출) — 묻는 단계 덕에 적용되진 않았다. 「아니, 문 막지 말고 벽을 뚫어서
새 통로를 내 줘」 → 「17번과 18번 매장 사이 벽에 3m 통로를 새로 낼게요. 적용할까요?」 →「응」→ 문 77→78. 다만 문이 **17번 앞 가로벽**에

### 2026-11-09 — Codex UX 시안 검토 (소유자: 「이런 식으로 더 간단하고 직관적인 게 낫지 않을까 — 똑같이 따라하라는 건 아님」)

시안(`floorplan-ux-mockup.html`, 예시 데이터)의 흐름: 01 도면 불러오기(업로드 | 샘플) → 02 도면 확인(한 줄로 접힘 + 「읽은 도면 확인」)
→ 03 왼쪽 도면(도면/히트맵 토글) · 오른쪽 「우선 검토할 구역」 2곳 → 구역을 고르고 「이 구역 수정하기」 → 예시 요청 「광장 쪽 벽에 문을 내줘」 →
「문 1개 추가 · 미리보기」(초록 점선) → **「적용하고 비교」** → 같은 도면에서 원본/수정안 전환 + 「동쪽 통로가 광장과 연결돼요 / 서쪽 복도는 그대로」.

**의견 — 방향은 맞다. 핵심은 「도구 중심 → 문제 중심」.** 지금 화면은 편집 도구 다섯 개·레이어·축척·인식 결과가 위에 늘어서 있어서 처음 온
사람이 무엇부터 할지 모른다. 가져올 것:
1. **문제에서 고치기로 바로** — 「우선 검토할 구역」 카드에 「이 구역 수정하기」. 누르면 그 구역이 고른 자리로 잡히고, AI 해석 「고칠 곳과 방법」의
   제안이 요청칸에 미리 들어간다(말로 고치기 2단계의 「이대로 고쳐 보기」와 같은 것). 도구를 고를 일이 없어진다.
2. **「적용하고 비교」를 한 번에** — 지금은 적용 → 「분석 실행」/「바꾼 것과 비교하기」를 따로 눌러야 한다. 적용하면 비교까지 돌리고, 같은 도면 위에서
   원본/수정안을 토글.
3. **도면과 결과를 나란히(넓은 화면)** — 지금은 도면 아래로 카드가 길게 내려간다. 휴대폰은 지금처럼 위아래.
4. **읽은 도면 확인은 한 줄로 접기** — 레이어·축척·실명 개수는 「읽은 도면 확인」을 열 때만.
5. 손 편집 도구(벽 그리기·문 뚫기·지우개)는 「직접 고치기」 안으로 접는다 — 지우지 않는다(말로 안 될 때 필요).

조심할 것: 시안의 구역은 깔끔한 예시라 「17번 매장 앞 통로」처럼 딱 떨어지지만, 우리 엔진의 문제 구역은 칸 덩어리라 이름이 늘 그렇게 나오진 않는다.
「물류센터 · 로봇 통로」 샘플은 같은 날 다른 세션이 샘플 버튼으로 붙였다(라이브 확인). 결정되면 위 1→2→4→3→5 순서로 새 세션에서.
