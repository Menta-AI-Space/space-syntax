## 0. 먼저 — 이미 있는 것과 없는 것

새로 짓는 설계가 아니다. **러너는 이미 24시간 돌고 있다.** 없는 것만 얹는다.

| 요구사항 | 지금 | 할 일 |
|---|---|---|
| 24시간 실행 | ✅ Railway `space-syntax-agent` | — |
| 개발 에이전트 2~3개 병렬 | ✅ worktree 격리 + 파일범위 충돌 방지 | — |
| 작업 큐·상태 보존 | ✅ `agent-state` 브랜치의 `task-state.json` | — |
| 실패 재시도 | ✅ 2회 후 blocked, 연속 3회면 정지 | — |
| 토큰 한도 대응 | ✅ rate_limit 감지 → 대기 후 재개 | — |
| **관리자 에이전트(계획·분배·검수)** | ❌ 정찰만 있음 | **만든다** |
| **텔레그램 입출력** | ❌ GitHub 이슈뿐 | **만든다** |
| **승인 필요 작업 분리** | ⚠️ 문서 규칙만, 강제 없음 | **만든다** |

## 1. 스택 확정 — 새로 도입하는 인프라는 **없다**

**결론: Railway 1개 서비스 + git = 끝.** VPS·Docker Compose·Redis·Celery·supervisor 전부 **쓰지 않는다.**

이유를 하나씩:

| 흔히 권하는 것 | 이 프로젝트에선 | 왜 |
|---|---|---|
| VPS(EC2/Vultr) | ❌ Railway 유지 | 이미 돌고 있고 PC를 꺼도 산다. 옮기면 SSH 키·방화벽·OS 패치가 새 숙제로 생긴다 |
| Docker Compose | ❌ 불필요 | Railway가 이미 `Dockerfile.agent`를 굽는다. Compose는 여러 컨테이너를 묶는 도구인데 컨테이너가 하나다 |
| Redis + Celery | ❌ 불필요 | 큐 처리량이 **시간당 10건 수준**이다. Redis는 초당 수천 건용이다. 지금 큐(JSON 파일)는 재시작해도 살아남고 git이 감사로그까지 준다 |
| systemd / supervisor | ❌ 불필요 | Railway의 `restartPolicyType: ALWAYS`가 같은 일을 한다 |
| tmux | ❌ 불필요 | 사람이 화면을 볼 때 쓰는 도구다. 무인 운영엔 로그가 답이다 |
| Claude Code 서브에이전트 | ⚠️ 부분 | 한 세션 안에서만 산다. 컨테이너가 죽으면 같이 죽는다. **프로세스 분리(`claude -p` 별도 호출)가 재시작에 강하다** — 지금 방식 유지 |

**"큐는 git"** 이 설계의 핵심이다. `agent-state` 브랜치의 `task-state.json`이 큐이고, 커밋 이력이 감사로그이며, force-push가 원자적 갱신이다. DB를 붙이면 백업·마이그레이션·접속정보가 새로 생기는데 얻는 게 없다.

### 프로세스 구성 (컨테이너 1개 안)

```
Railway 컨테이너
├─ telegram_bot.py   (폴링, 가벼움)  ← 새로 만듦
│     받은 지시 → task-state.json에 작업 추가 → 즉시 "접수" 응답
│     러너가 남긴 알림 → 텔레그램 전송
└─ runner.py         (이미 있음)
      매 사이클: 관리자 호출 → 개발자 2개 병렬 → 검증 → push → 상태 기록
```

두 프로세스는 **파일로만 대화한다**(`task-state.json` + `outbox.jsonl`). 소켓도 큐도 없다. 한쪽이 죽어도 다른 쪽은 산다.

### 충돌 방지 — 지금 방식 유지 + 한 가지 추가

이미 3중으로 막혀 있다:
1. 작업마다 `files` 소유 범위 — 겹치면 **같은 회차에 안 뽑는다**
2. 작업마다 별도 git worktree — 파일이 서로 안 보인다
3. push는 `_PUSH_LOCK`으로 한 번에 하나

추가할 것 하나: **관리자가 작업을 쪼갤 때 `files`를 반드시 disjoint하게 적도록 강제.** 겹치면 관리자에게 되돌려 다시 쪼개게 한다. 지금은 관리자가 없어서 정찰이 대충 적으면 그대로 들어간다.

브랜치 전략은 **main 직행 유지**(검증 통과분만). `auto/*`+PR은 이미 한 번 실패했다 — 101개가 쌓이고 병합은 0건이었다. 되돌릴 이유가 없다.

## 2. 텔레그램 연동

### 흐름

```
① 나: "입지 점수 화면에 그래프 추가해줘"
        ↓ (봇이 3초 안에)
② 봇: "접수했어요. 관리자가 작업을 쪼개는 중… [T-211]"
        ↓
③ 관리자 에이전트: 저장소를 읽고 3개로 쪼갬 + 파일범위 배정 + 승인필요 판정
        ↓
④ 봇: "3개로 나눴어요:
        T-211 백엔드 시계열 필드 (예상 60분)
        T-212 차트 컴포넌트 (예상 90분)
        T-213 화면 연결 (예상 45분)
        시작합니다."
        ↓
⑤ 개발 에이전트 2개 병렬 실행 → 검증 → push
        ↓
⑥ 봇: "T-212 완료 ✅
        테스트 802 passed / lint clean
        변경: TrendsChart.tsx (신규 140줄), api.ts (+3줄)
        확인 필요: 모바일 390px에서 축 라벨이 겹칠 수 있어요"
```

**즉시 응답이 중요하다.** 봇은 지시를 받으면 관리자를 기다리지 않고 바로 "접수" 를 답한다. 관리자 호출은 1~3분 걸리므로, 기다리게 하면 죽은 봇처럼 보인다.

### 왜 폴링인가

웹훅은 공개 URL + HTTPS 인증서 + 그 URL을 아무나 두드릴 수 있는 위험을 만든다. 폴링(`getUpdates`)은 컨테이너가 텔레그램에 **나가서** 물어보는 방식이라 열어 줄 포트가 없다. 하루 수십 건 규모에서 폴링의 단점(약간의 지연)은 무의미하다.

### 승인 분리 — 규칙이 아니라 코드로

지금은 CLAUDE.md에 "이런 건 승인받아라"라고 **적혀만** 있다. 관리자 에이전트가 그걸 어기면 막을 게 없다. 그래서 작업에 플래그를 둔다:

```json
{
  "id": "T-214",
  "title": "옛 real_estate_trades 테이블 삭제",
  "needs_approval": "운영 데이터 삭제",
  "status": "awaiting_approval"
}
```

`awaiting_approval`은 러너가 **절대 안 뽑는다**. 봇이 텔레그램으로 버튼을 보낸다:

```
⚠️ 승인이 필요해요
T-214 옛 real_estate_trades 테이블 삭제
사유: 운영 데이터 삭제
[승인] [거절] [나중에]
```

승인 판정은 **관리자 에이전트의 판단에 맡기지 않는다.** 작업 제목·파일범위를 규칙으로 검사한다(코드로):

| 자동 진행 | 승인 필요 |
|---|---|
| 코드 수정·테스트 추가 | DB 스키마 변경, 데이터 삭제 |
| 화면·문구 개선 | 시크릿·권한·`.github/workflows/` 변경 |
| 리팩터링, 버그 수정 | 유료 서비스 가입·결제 |
| 문서 갱신 | 파일 20개 이상 삭제 |
| | 외부로 메시지 전송 |

규칙에 안 걸려도 관리자가 "이건 사람이 봐야 한다"고 판단하면 플래그를 **추가**할 수는 있다. 뺄 수는 없다 — 한 방향으로만 움직인다.

## 3. 24시간 안정성

### 이미 있는 것

- 컨테이너 죽음 → Railway 자동 재시작 → `agent-state`에서 기억 복원
- 작업 실패 → 2회 재시도 → blocked로 격리 (무한 재시도 안 함)
- 연속 3회 실패 → 전체 정지 + 알림 (망가진 채로 계속 미는 것 방지)
- 토큰 한도 → 15분 대기 후 재개, 실패로 세지 않음
- 작업 시간 초과 → kill + 사유 기록 (기본 20분, 작업별 최대 4시간)

### 추가할 것

| 위험 | 대응 |
|---|---|
| 러너가 살아는 있는데 아무것도 안 함 | **워치독**: 3시간 이상 상태 변화가 없으면 텔레그램 알림 |
| 같은 작업을 무한 재발견 | 이미 있음(제목 유사도 + 파일범위 dedup). 추가로 **하루 신규 작업 상한 20건** |
| 로그가 컨테이너와 함께 증발 | 실패 사유는 이미 `FAILURES.md`로 git에 남는다. **로그 보관 30일**은 Railway 기본으로 충분 |
| 검증이 통과했는데 화면이 깨짐 | §4 gstack 게이트 |

## 4. gstack을 품질 게이트로

### 순서

```
[관리자] 계획 수립
    ↓
  /plan-eng-review  ← 계획 단계 검토 (구현 전에 잘못된 방향을 잡는다)
    ↓
[개발자] 구현
    ↓
  pytest + typecheck + test + lint     ← 이미 있음. 여기 실패하면 push 안 함
    ↓
  /review           ← 코드 리뷰 (논리 결함·엣지케이스)
    ↓
  /qa 또는 /browse  ← 화면이 바뀐 작업만. 실제 브라우저로 확인
    ↓
[관리자] 검수 → 통과하면 push
```

**정직한 주의**: gstack 스킬들이 무인(`claude -p`) 환경에서 어떻게 동작하는지는 **아직 검증 안 됐다.** 대화형 전제로 만들어진 스킬이 섞여 있다. 그래서:

- **MVP에서는 넣지 않는다.** 지금 게이트(pytest·typecheck·test·lint)로 간다.
- **안정화 단계에서 `/review` 하나만** 먼저 붙여 1건으로 실제 되는지 확인하고, 되면 나머지를 늘린다.

이 순서를 지키지 않으면 "리뷰가 도는 줄 알았는데 조용히 건너뛰고 있었다"가 된다 — 이 프로젝트에서 이미 여러 번 당한 실패 방식이다.

### "완료"의 정의

에이전트가 done이라고 적으려면 **전부** 만족해야 한다:

1. 백엔드 `pytest -q` 통과
2. 프론트 `typecheck && test && lint` 통과
3. 변경 파일이 배정된 `files` 범위 안
4. main에 **실제로 push됨** (push 실패 = 미완료)
5. 화면이 바뀐 작업이면 브라우저 확인 결과 첨부

지금 4번까지는 강제되고 있다. 5번이 빠져 있고, 그게 "테스트는 통과했는데 화면은 아무도 안 봤다" 문제의 원인이다.

## 5. 보안·비용

### 텔레그램 권한

```python
ALLOWED_USER_IDS = {123456789}   # 내 텔레그램 숫자 id만
```

username(`@handle`)이 아니라 **숫자 id**로 검사한다 — username은 남이 바꿔서 가로챌 수 있다. 목록에 없는 사람의 메시지는 **조용히 버린다**(응답하면 봇이 살아 있다는 걸 알려 주는 꼴이다).

### 키 관리

| 값 | 어디에 | 절대 안 되는 곳 |
|---|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` | Railway 변수 (이미) | 코드, 대화창, 커밋 |
| `GH_TOKEN` | Railway 변수 (이미) | 〃 |
| `TELEGRAM_BOT_TOKEN` | Railway 변수 (새로) | 〃 |
| `TELEGRAM_ALLOWED_IDS` | Railway 변수 (새로) | 〃 |

GitHub 토큰 권한은 지금 그대로 유지: `space-syntax/space-syntax`만, Contents+Issues+Metadata. **Workflows 권한은 절대 켜지 않는다** — 켜면 러너가 배포 워크플로 자체를 고쳐 쓸 수 있다.

### 비용

**추가 API 비용 0원이 목표이고 지금 그렇다.** 구독 토큰(`claude setup-token`)으로 인증하므로 이미 내는 구독으로 청구된다. `ANTHROPIC_API_KEY`가 환경에 있으면 그쪽이 우선해서 **과금이 시작되므로**, 러너는 그 키가 보이면 아예 시작을 거부한다(이미 구현됨).

무한루프 방지 3중:
- 작업당 시간 상한 (기본 20분 / 최대 4시간)
- 재시도 2회 후 blocked
- 연속 실패 3회면 전체 정지 + 알림

여기에 추가: **하루 신규 작업 20건 상한**, **하루 총 실행시간 상한**(예: 16시간).

## 6. 단계별 계획

### 🟢 MVP — 1주일 (가치의 80%)

텔레그램 입출력만. 관리자·gstack 없이 **지금 러너에 말을 걸 수 있게** 하는 것이 목표.

| 할 일 | 누가 |
|---|---|
| BotFather로 봇 생성 → 토큰 발급 | **회원님** |
| 본인 텔레그램 숫자 id 확인 (`@userinfobot`) | **회원님** |
| Railway 변수 2개 입력 | **회원님** |
| `backend/tools/agent/telegram_bot.py` 작성 | Claude |
| 작업 추가·상태 조회·알림 전송 로직 | Claude |
| 권한 검사(숫자 id 화이트리스트) | Claude |
| `Dockerfile.agent`·entrypoint에 봇 프로세스 추가 | Claude |
| 승인 플래그(`awaiting_approval`) + 버튼 | Claude |

이 단계 끝나면: **"이거 고쳐줘" → 접수 응답 → 완료 보고**가 된다. 작업 쪼개기는 아직 내가(=Claude가) 한 단위로 넣는다.

### 🟡 안정화 — 2~3주차

| 할 일 | 누가 |
|---|---|
| 관리자 에이전트(`manager.py`) — 계획·분배·검수 | Claude |
| `files` disjoint 강제 검사 | Claude |
| 워치독(3시간 무변화 알림) | Claude |
| `/review` 게이트 1건 실검증 → 되면 상시 적용 | Claude |
| 하루 작업/시간 상한 | Claude |
| 관리자 판단 품질 확인 (쪼갠 결과를 몇 건 읽어 보기) | **회원님** |

### 🔵 확장 — 그 이후

- 브라우저 E2E 게이트 (`/qa`) — 화면 변경 작업의 5번 완료 조건
- 아침 요약 보고 (밤새 한 일 + 확인 필요 항목)
- 여러 저장소 지원 (mall-flow, seller-copilot 등)
- 작업별 소요시간·성공률 통계

## 7. 회원님이 직접 해야 하는 일 (전부)

MVP 기준 **딱 3가지**, 10분이면 끝난다.

1. **텔레그램에서 `@BotFather` 검색 → `/newbot` → 이름 정하기 → 토큰 받기**
2. **`@userinfobot`에게 아무 말이나 보내기 → 내 숫자 id 확인**
3. **Railway → `space-syntax-agent` → Variables에 2개 추가**
   - `TELEGRAM_BOT_TOKEN` = 1번에서 받은 값
   - `TELEGRAM_ALLOWED_IDS` = 2번에서 본 숫자

**토큰을 대화창에 붙여넣지 마세요.** Railway 변수 칸에 직접 넣으면 됩니다. 나머지 코드·배포는 전부 Claude가 합니다.
