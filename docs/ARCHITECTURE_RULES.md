# 아키텍처 규칙 — 데이터 적재, 응답 시간, 도면 분석

## 공공데이터는 API 실시간 호출이 아니라 파일로 받아 DB에 적재한다

정부·공공 데이터 API는 느리고(초 단위) 호출 제한이 있고 가끔 죽는다. 사용자 요청마다
부르면 5초 룰을 못 지킨다. 그래서 기본 경로는:

1. `backend/tools/ingest_*.py`로 원본 파일/API에서 통째로 받는다 (한 번 또는 배치).
2. PostGIS/Postgres에 적재한다 (`subway_ridership`·`real_estate_trades`·
   `living_population`·`land_prices`가 이 패턴).
3. 서비스 코드(`app/routers/`, `app/services/`)는 그 로컬 테이블만 조회한다. 런타임에
   외부 API를 부르지 않는다.

**예외**: Kakao geocoding(`app/services/geocoding.py`)처럼 요청마다 값이 달라지고 미리
적재할 수 없는 경우만 실시간 호출.

**새 소스를 붙이기 전에**: 원하는 필드가 정말 그 API/오픈데이터에 있는지 먼저 검증한다.
통계 API에는 없고 원문 문서(PDF 등)에만 있는 필드도 있다 — 그땐 API 신청보다 원문을
파싱하는 게 맞다.

## 5초 룰과 그 유일한 예외 — 도구 루프 상담 경로 (2026-08-24)

모든 분석은 5초 안에 나와야 한다. **예외는 하나뿐이다**: `/api/agent/ask`의 도구 루프
경로(`settings.agent_loop_enabled`, `app/services/agent_loop.py`). 라이브 실측으로 도구를
부르는 질문은 **9~26초**가 걸린다(도구 3개 26초, 2개 9초, 도구 없는 개념 질문 8초).
소유자가 속도가 아니라 **깊이**를 택했다.

바꾼 이유는 종전 경로가 빠른 대신 **다른 질문에 답하고 있었기** 때문이다. 같은 문장
("신촌역 근처에 월세 300만원짜리 카페 자리 계약해도 될까?") 라이브 실측:

| | 기존 경로 | 루프 |
| --- | --- | --- |
| 결과 | `mode=talk` — "어느 동네인지 없어서 못 돌린다"고 되물음 | `mode=analyze` · 신촌역 · 카페 |
| 도구 | 없음 | `lease_verdict`+`lease_feasibility`+`real_competition` (모델이 스스로 고름) |
| 답 | 일반론 517자 | **보류** — 적정 월세 234만원 대비 66만원 초과 |
| 시간 | 5.8초 | 25.7초 |

도구를 부르지 않는 기본 경로(site_score)와 대시보드·분석 API는 여전히 5초를 지킨다.
프론트·프록시 타임아웃은 양쪽 330초라(`frontend-next/lib/api.ts`,
`app/api/[...path]/route.ts`) 이 지연으로 깨지지 않는다.

라이브에서 **켜져 있다**: `space-syntax` 프로젝트 / `backend` 서비스에
`AGENT_LOOP_ENABLED=true`. 코드 기본값은 `False`이므로 **저장소만 보고 꺼져 있다고
판단하지 말 것.** 되돌리려면:

```bash
railway variables -s backend --set AGENT_LOOP_ENABLED=false
```

지연이 문제면 끄기 전에 예산부터 조인다 — `agent_loop.py`의 `MAX_ROUNDS`(3)와
`MAX_CALLS_PER_ROUND`(3)를 각각 2로 내리면 10~15초대가 된다.

## 도면 분석(실내 VGA) — DXF만 받는다 (2026-08-23)

`/api/floorplan/extract`는 **DXF만 받는다.** 사진·스캔 이미지(JPEG/PNG) 업로드는
프론트(`accept=".dxf"`)와 백엔드(`floorplan.py`) 양쪽에서 막는다 — 하나만 막으면 API를
직접 두드리는 경로가 남는다.

이유는 실측이다. 유리 안내판을 비스듬히 찍은 사진(Lulu Mall 샘플)은 원근왜곡·반사로
OpenCV 벽 인식이 건물 봉투를 완성하지 못해 실내/실외 구분 같은 후속 로직이 다 무너진다.
벡터에서 렌더한 깨끗한 도면(WTC 샘플, PNG)은 잘 되지만 그건 "이미지라서"가 아니라
"원래 벡터였던 걸 다시 래스터화했을 뿐"이라서다. 갈리는 기준은 파일 형식이 아니라
**정면에서 그린 벡터 도면이냐 vs 사진이냐**이고, DXF는 그 벡터를 직접 받으니 OpenCV
추정 단계가 아예 필요 없다. `extract_from_image`(OpenCV/Hough)는 지우지 않고 남겨 뒀다 —
라우터에서만 막았다.

`floorplan_vga.py`는 networkX가 아니라 scipy/numpy 자체 구현이다 (networkX는 도로망 쪽
`space_syntax.py`에서만 쓴다). Choice(매개중심성)도 같은 이유로 희소 행렬 mat-vec Brandes로
직접 구현했고(2026-09-17), 800칸을 넘으면 피벗 400개를 표본해 5초 룰을 지킨다 — 정확값이
필요한 곳(테스트)은 `_choice(adjacency, None)`. 축척은 DXF `$INSUNITS`에서 읽고, 없으면
프론트가 가로 길이(m)를 받는다.

**depthmapX CLI 전환은 보류.** `depthmapx_engine.py`에 CLI 다리가 있지만 도로망
(segment-angular) 전용이고 `DEPTHMAPX_COMMAND`가 비면 안 쓰는 선택적 경로다. 선택적인
이유가 도면 쪽에도 그대로 적용된다: depthmapXcli는 컴파일된 Qt 데스크톱 프로그램이라
로컬 Windows에선 되지만 운영(Railway, Linux 컨테이너)에 못 올릴 가능성이 크다. 로컬
검증용 브리지를 먼저 만들고 운영 배치 가능 여부를 확인한 뒤 승격 여부를 정한다. 그
전까지 `floorplan_vga.py`(scipy VGA)가 유일한 계산 경로다.
도면용 브리지(`floorplan_depthmapx_engine.py`)는 2026-10-25에 고쳐 **대조 검증 기준**으로만 쓴다 —
`tests/test_floorplan_depthmapx_parity.py`가 depthmapXcli 있는 랩탑에서 칸별로 맞춰 본다(없으면 skip).

테스트용 대형 몰 DXF: `frontend-next/public/samples/synthetic-large-mall.dxf` (합성 —
실제 무료 CAD 사이트는 DWG 위주에 라이선스가 불분명해 커밋하지 않았다). 240m×120m,
중앙 통로 + 양끝 앵커 매장 + 통로 양옆 매장 20개, WALL/DOOR 레이어 분리. 파이프라인
통과 확인(2026-08-23): 벽 46개·문 36개, 반영률 97%, 1.74초.

## DWG를 직접 읽을 것인가 — 라이선스가 갈림길이다 (2026-09-30 조사, 미결)

실무 도면은 **DWG**로 돈다. DXF는 교환용이라 사무소가 평소 들고 있지 않아, "DXF로
저장해서 주세요"가 진입 장벽이 된다. 그래서 DWG 지원을 검토했고, **결정은 소유자
몫으로 남긴다** — 코드 문제가 아니라 라이선스·비용 문제이기 때문이다.

| 안 | 어디서 변환 | 라이선스 | 비용 | 위험 |
| --- | --- | --- | --- | --- |
| A. 브라우저 WASM (`@mlightcad/libredwg-web`) | 손님 PC | **GPL-3.0** | 0 | ⚠️ **배포에 해당한다.** 우리 프론트가 GPL 바이너리를 브라우저로 내려보내므로 결합저작물 논란이 생긴다. 상용 제품에서 가장 위험한 선택 |
| B. 서버에서 변환 (LibreDWG `dwg2dxf`) | 우리 서버 | GPL-3.0 | 0 | ✅ **배포가 아니다.** GPL-3에는 AGPL 같은 네트워크 조항이 없어 SaaS 내부 사용은 의무가 생기지 않는다. 다만 Debian 기본 패키지에 없어 도커에서 소스 빌드가 필요하다 |
| C. 유료 SDK (ODA Teigha 등) | 우리 서버 | 상용 | 연간 비용 | ✅ 가장 안전·정확. 돈이 든다 |
| D. 지금처럼 DXF만 | — | — | 0 | 손님에게 변환을 시킨다 |

**처음엔 A를 추천했지만 조사 결과 뒤집혔다.** "서버를 안 건드려서 안전하다"고 봤는데,
라이선스 관점에서는 A가 가장 위험하고 **B가 안전하다**. 도면이 서버에 올라가지 않는
장점은 A에 있으나, 그 장점을 위해 GPL 결합 위험을 지는 건 균형이 맞지 않는다.

**B를 고를 경우 할 일**: `python:3.11-slim`에 빌드 의존성(gcc·autoconf·libtool)을 넣고
LibreDWG를 컴파일 → `dwg2dxf`로 변환 후 기존 DXF 경로로 흘린다. 도커 빌드가 무거워지고
(현재는 depthmapX 바이너리 하나만 내려받는 단순한 구조), 2026-09에 배포가 8일간 멈춘
전례가 있으므로 **배포 파이프라인이 안정된 상태에서 손대야 한다.**

**그 전에 확인할 것**: DWG를 읽어도 레이어 이름을 못 알아들으면 벽 인식이 안 된다.
레이어 선택 화면(2026-09-30)이 그 문제를 이미 흡수했지만, **실제 사무소 DXF로 인식률을
먼저 확인하는 것이 순서다.** 파일 형식을 넓히는 일은 그다음이다.

## 도면을 고치라고 하지 않는다 — 정규화는 우리 일이다 (2026-10-01 결정)

**손님은 건축사사무소에서 받은 파일을 그대로 넣고 바로 결과를 본다.** "한 평면만
남기고 잘라서 올려 주세요"·"어느 레이어가 벽입니까"·"XREF를 BIND해 주세요"는
우리가 할 일을 손님에게 넘기는 것이고, 일반 사용자는 그걸 못 한다. 불편하면 안 쓴다.

실제 사무소 도면 3장(2026-10-01)으로 확인한 실상:

| 파일 | 실제 모습 |
| --- | --- |
| `1층평면도.dwg` | `WA1`엔 세대 내부 벽만. 외벽 레이어가 따로 있고 조경선과 섞여 있다 |
| `1층평면도(1).dwg` | 1,401 × 2,129m. 좌표가 튀어 있다 |
| `PLAN-1ST FLOOR.dwg` | 1,529 × 368m 한 장에 **작은 평면 12개**가 흩어져 있다 |

그래서 `extract_from_dxf`에 **도면 정규화** 단계를 넣었다. 사람이 레이어를 직접
고르기 전에 프로그램이 한다 (사람이 고른 뒤에는 **사람 선택이 늘 이긴다**):

1. **한 장에 도면이 여럿이면 하나를 골라 자른다.** 선 전체로 덩어리를 찾고,
   그중 **벽이 가장 많이 든 덩어리**를 고른다. 크기로 고르면 벽이 없는 옆 도면을 집는다.
2. **이름으로 찾은 벽만으로 외곽이 안 닫히면 닫히는 레이어를 찾아 더한다.**
   (`floorplan_layer_advice.suggest_wall_layers`)
3. 한 일은 `auto_notes`로 돌려주고 화면이 「이렇게 읽었습니다」로 보여 준다 —
   **경고가 아니다.** 손님은 확인만 하고, 틀렸을 때만 레이어 목록에서 손댄다.

### 점수 매기는 방식 — 세 번 틀렸다

후보 레이어를 넣어 보고 「건물이 닫히나」로 고르는데, 그 "닫힘"을 재는 법이 문제였다.
**버린 방식과 이유를 적어 둔다. 안 적으면 되돌아간다.**

| 방식 | 뽑힌 것 | 왜 틀렸나 |
| --- | --- | --- |
| 선이 감싼 경계 상자 대비 실내 비율 | `A-SP-LOT`·`DefPoints` | 건물이 아니라 **땅**을 감싸 놓고 점수가 올랐다 |
| + "상자를 넓히는 후보는 거절" | — | 외벽이 조경선과 **한 레이어에 섞이면** 같이 거절된다 |
| 실내 **면적 합계** | `fin` 2,705㎡ | 그려 보니 **포장 해치**였다. 선 사이에 갇힌 자잘한 칸으로 점수를 벌었다 |
| **가장 큰 실내 덩어리 하나** ← 채택 | — | 해치는 덩어리가 잘다. 진짜 외벽은 큰 덩어리를 만든다 |

덩어리를 찾는 격자 칸은 **실치수 1m로 고정**한다. 도면 크기에 비례시키면 1,500m
종이에서 칸이 17m가 되어 평면도 여러 개가 한 덩어리로 뭉친다.

⚠️ **그림으로 확인하지 않으면 다 그럴듯해 보인다.** 위 세 방식 모두 숫자는 좋았다
(95%, 2,705㎡). 틀린 걸 안 건 추천 조합을 PNG로 그려 보고 나서다.

### 아직 손님에게 넘기고 있는 것 (다음 차례)

- **DWG를 못 받는다.** 사무소는 DWG를 준다. "DXF로 저장해 주세요"가 지금 가장 큰 마찰이다
  (위 §「DWG를 직접 읽을 것인가」 — 미결).
- **XREF가 걸린 파일.** 참조된 파일이 없으면 기하가 없다. 여러 파일을 한 번에 받아
  참조를 풀어 주는 쪽이 답이다.
- **외곽이 끊긴 도면에 "'벽 그리기'로 이어 주세요"** 라고 한다. 자동 봉합 커널이
  이미 있으니(`_SEAL_KERNELS`) 거기서 더 밀어붙일 여지가 있다.

### 자동 봉합을 파 보니 — 봉합이 아니라 이름과 그리는 순서가 문제였다 (2026-10-01)

"외곽이 끊겼으니 '벽 그리기'로 이어 주세요"를 없애려고 들어갔는데, 실제 원인은
봉합이 아니었다. 모폴로지 닫힘은 이미 커널 31까지 돌고 있었다. 고친 둘:

1. **문·창 이름을 못 알아봤다.** 실무 도면은 `A-DR-FUL`(문)·`A-WX-SIL`(창)처럼
   두 글자로 줄여 쓴다. `door`·`window`만 찾던 탓에 `PLAN-1ST FLOOR.dwg`은
   **문이 0개**로 읽혀 방이 44조각으로 끊겼다. 벽 토큰(`wa`·`wl`)과 같은 규칙으로
   `dr`·`wx` 접두를 추가했다. `gls`는 일부러 뺐다 — `A-WL-GLS`는 유리벽이다.
2. **개구부를 벽과 함께 그리지 않았다.** 문·창 자리는 실제로 벽체가 있는 자리다.
   안 그리고 비워 두면 외벽에 구멍이 남아 바깥이 새어 들어온다. ①을 고친 직후
   창틀을 알아보자마자 외곽 비율이 80%→52%로 **떨어졌다** — 알아본 것이 손해가
   되면 안 된다. 이제 `walls + openings`로 격자를 그린 뒤 개구부만 뚫는다.
   (외곽 비율: `1층평면도(1)` 21%→28%, `PLAN-1ST FLOOR` 52%→59%)

**버린 안: 고른 도면을 「덩어리 모양」으로 자르기.** 경계 상자로 자르면 옆 도면과
기둥 마커가 딸려 온다는 진단까지는 맞았는데, 모양으로 자르니 `1층평면도`의 외벽
레이어가 함께 잘려 반영률이 94%→72%로 떨어지고 `PLAN-1ST FLOOR`는 9m 격자짜리
띠로 무너졌다. 되돌렸다.

⚠️ **`PLAN-1ST FLOOR`의 낮은 수치를 근거로 쓰지 말 것.** 이 파일은 DWG를
JSON으로 뽑아 DXF로 되쓴 것인데(`tools/dwg_json_to_dxf.py`), 그 변환이 **블록
안을 버린다.** 문·가구가 블록에 들어 있으면 통째로 사라진다. 실제로 이 파일엔
블록이 0개다. 더 밀어붙이기 전에 변환기가 블록을 펼치게 고치는 것이 먼저다.
