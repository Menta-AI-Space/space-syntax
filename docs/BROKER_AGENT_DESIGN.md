# 중개사용 연락 Agent — 설계 문서 (v0, 코드 전 설계 단계)

> 상권분석 엔진을 그대로 재사용하되, **중개사가 고객·매물을 관리하고 "누구에게
> 언제 무슨 연락을 할지"를 대신 정리·초안해 주는** AI 비서. Intercom Fin의
> "역할 카드" UX + MindStudio가 정리한 부동산 AI agent 10종 중 **현실적으로 2인
> 팀이 지금 만들 수 있는 것**만 추린다.

---

## 0. 한 줄 정의

중개사가 상담·매물 정보를 **말/입력하면** 고객·매물 카드가 자동 정리되고, 서로
맞는 고객↔매물을 찾아주며, **연락 메시지 초안과 다음 할 일**까지 만들어 주는
비서. 매물엔 우리 상권분석이 자동으로 붙는다(← 이게 남들과의 차별점).

---

## 1. 아키텍처 결정 — 왜 별도 서비스인가

| | 상권분석 사이트 (기존) | 중개사 비서 (신규) |
|---|---|---|
| 상태 | **무상태** — 요청→분석→응답 | **상태저장** — 고객·매물·연락 이력이 쌓임 |
| 개인정보 | 없음 | **있음** (고객 이름·전화) |
| 배포 | push=즉시 라이브, 작은 단위 자주 | 반쯤 만든 상태로 몇 주 |
| 사용자 | 누구나(익명) | 로그인한 중개사 |

→ **분석 엔진은 안 건드린다.** 중개사 비서는 **새 서비스/레포**로, 분석은
`space-syntax-production...`을 **HTTP로 호출**해서 매물에 붙인다. UI만 지금
카드홈에 "중개사 업무" 역할군으로 얹어 한 제품처럼 보이게 한다.

미국판 `real-estate-agent`(AgentPilot)에 leads/listings/comps 스키마 +
규칙기반 스코어링이 이미 있다 → **구조는 재사용, 필드는 한국 상업용으로 교체**
(beds/baths/sqft → 보증금/월세/권리금/배기/전용평).

---

## 2. 절대 규칙 3가지

1. **자동 발송 금지.** 연락 agent는 **초안까지만**. 초안 → 중개사 승인 →
   복사/발송. 카톡 자동발송은 정책·계정 문제로 v1에서 뺀다.
2. **숫자·판정은 규칙 엔진(결정론적), 문장만 LLM.** 같은 입력=같은 결과.
   나중에 로컬 LLM으로 갈아끼워도 순위·트리거가 안 바뀌게.
3. **AI가 DB를 직접 못 고친다.** AI는 구조화된 변경안을 만들고 → 화면에
   미리보기 → 중개사 확인 → 서버가 확정 저장.

## 3. 데이터 스키마 (초안)

```
clients (고객)
  id, name, phone, memo,
  purpose            -- 임차|매수
  category           -- 업종 (카페/음식점/학원…)
  region             -- 희망 지역 (동/역 텍스트 + 선택 lat/lng)
  deposit_max_man    -- 보증금 상한(만원)
  rent_max_man       -- 월세 상한(만원)
  floor_pref         -- 1층|무관…
  must_haves         -- 배기·주차 등 (태그 배열)
  priority           -- 가시성|월세|면적… (정렬 가중치)
  stage              -- 신규|상담중|방문예정|계약임박|보류|완료
  created_at, last_contact_at, next_followup_at

listings (매물)
  id, address, lat, lng,
  category_ok        -- 허용 업종 (태그)
  floor,
  area_pyeong        -- 전용 평
  deposit_man, rent_man, mgmt_man, key_money_man,
  facilities         -- 배기·급배수·전력·주차 (태그)
  available_from,
  status             -- 확인전|오늘확인|7일+미확인|계약완료|보류|비공개
  verified_at,
  site_analysis_json -- 상권분석 엔진 응답 캐시(주소 기준)

contacts (연락 로그)
  id, client_id, listing_id?, channel, direction, summary, created_at

consultations (상담 결과)
  id, client_id, transcript_raw, parsed_json, created_at

tasks (할 일)
  id, client_id?, listing_id?, kind, due_at, done, note
```

## 4. 규칙 엔진 — "오늘 연락할 고객" (결정론적)

각 고객에 **연락 우선순위 점수**를 매기고 상위 N명을 뽑는다. 전부 규칙, LLM 없음:

```
+30  next_followup_at 이 오늘 이전 (약속한 후속연락일 지남)
+25  stage=계약임박  / +15 방문예정 / +8 상담중
+20  관심 조건에 맞는 매물이 최근 7일 내 신규 등록됨
+15  last_contact_at 이 (단계별 기준일) 초과   -- 계약임박 3일, 상담중 7일, 신규 14일
-40  stage=보류 또는 완료
```

→ 점수·이유를 그대로 화면에 표시("월세 400 이하 신촌 1층 신규매물 2건 등장 +20").
**왜 연락해야 하는지**가 숫자로 보이는 게 핵심.

---

## 5. 매칭 규칙 — 고객 ↔ 매물 (결정론적)

첫 버전은 AI 추천모델 없이 규칙 점수 100점 만점:

```
필수조건(must_haves) 불충족 → 즉시 제외 (예: 배기 필수인데 없음)
+  지역 근접        (거리 가까울수록)
+  월세 예산 이내    (초과 시 초과분만큼 감점)
+  보증금 예산 이내
+  업종 허용
+  층 선호 일치
+  면적 범위
+  입주 가능일
```

출력엔 항상 **불일치 이유**를 같이("월세 50만원 초과, 주차 조건 불일치").
데이터가 쌓이면 나중에 방문/거절/계약 결과로 가중치를 학습.

## 6. 화면 4개 (Fin식 역할 카드)

지금 "무엇을 결정하려고 하시나요?" 카드홈에 **중개사 역할군** 추가:

1. **오늘 연락할 고객** — §4 점수 순 리스트. 각 항목에 "왜"와 [메시지 초안] 버튼.
2. **이 고객에게 맞는 매물 / 이 매물에 맞는 고객** — §5 양방향 매칭 + 이유.
3. **제안·연락 메시지 초안** — 상위 매물 비교 + LLM 초안 + [복사]. (발송 안 함)
4. **상담 결과 기록** — 말한 내용 → 조건·일정·다음 할 일로 자동 파싱(미리보기→확인).

추가 화면: **오늘 할 일** 대시보드(연락할 고객 + 방문 일정 + 오래 미확인 매물).

## 7. 상권분석 엔진 연동

매물 등록 시 주소로 분석을 한 번 호출해 `site_analysis_json`에 캐시:
- 호출: 기존 `/api/dashboard` 또는 `/api/site-score` (주소→lat/lng는 엔진의
  Kakao geocoding이 처리).
- 중개사에겐 원점수 대신 **고객에게 설명할 문장**으로 요약("카페 적합성 높음 —
  20~30대 배후수요 크고 가시성 좋음, 동일업종 경쟁은 강함").
- 5초 룰: 등록 시 1회 캐시 → 이후 재조회는 로컬 캐시. (공공데이터 원칙 그대로)

## 8. LLM 경계 (넣는 것 / 만드는 것)

| LLM에 **넣는** 것(이미 결정된 사실) | LLM이 **만드는** 것 |
|---|---|
| 매칭 점수·이유, 매물 숫자, 고객 조건, 분석 요약 | 고객에게 보낼 **메시지 문장** |
| 상담 원문(음성/텍스트) | 원문 → **구조화 JSON**(조건·일정·할일) |

숫자·순위·트리거는 절대 LLM이 만들지 않는다. 로컬 LLM 전환 대비.

---

## 9. 첫 슬라이스 (1주, 가치 증명)

화면 4개 다 만들지 말고 **①오늘 연락할 고객 + ③메시지 초안** 둘만:

1. 고객 몇 명을 수기/엑셀로 입력 (스키마 §3 최소 필드)
2. §4 규칙이 오늘 연락 대상 + 이유 뽑음
3. 버튼 누르면 LLM이 연락 초안 → 복사

→ 중개사 1명한테 실제 고객 엑셀 받아 넣어보면, 나머지(매칭·상담기록)를 만들
가치가 있는지 **3일이면** 안다.
