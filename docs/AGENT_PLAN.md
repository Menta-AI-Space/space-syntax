# 자율 에이전트 작업 계획서 (agent/auto-work)

이 문서는 클라우드에서 매시간 도는 자율 에이전트가 **매번 세션을 새로 시작하며 처음 읽는 문서**다.
로컬 세션의 기억(메모리)에 접근할 수 없으므로, 방향과 진행 상황은 전부 이 파일에 있어야 한다.

## 안전 규칙 (반드시 지킬 것)

1. **이 브랜치(`agent/auto-work`)에서만 작업한다. `main`에 직접 push 금지.**
   이 저장소는 `main`에 push되면 GitHub Actions가 즉시 Railway/Firebase에 배포한다
   (`.github/workflows/deploy.yml`, `CLAUDE.md` 참고). 무인 자율 실행이 실수로 라이브를
   깨뜨리면 안 되므로, `main` 병합은 사람(오너 또는 채연)이 검토 후 한다.
2. **커밋 전 반드시 검증**: 백엔드는 `cd backend && .venv\Scripts\python -m pytest tests/ -q --ignore=tests/test_ingest_hira_specialty.py`
   (openpyxl 미설치로 이 파일만 무관하게 실패, 그 외 전부 통과해야 함),
   프론트는 `cd frontend-next && npm run typecheck && npm test`.
3. **`git pull origin agent/auto-work`로 시작** — 이전 실행이 이미 진행해둔 것을 다시 하지 않는다.
   브랜치가 없으면 `git fetch origin && git checkout agent/auto-work` (원격에 있음).
4. 작업이 끝나면 **이 문서의 "진행 상황" 섹션을 갱신**하고 커밋에 포함한다. 다음 실행이 여기를 읽는다.
5. 판단이 필요한데 확신이 안 서면, 막히지 말고 **가장 안전한 쪽으로 진행**하고
   "질문/확인 필요" 섹션에 남긴다. 실행을 멈추지 않는다.
6. 로컬 PostGIS 없이도 `frontend-next/.env.local`에
   `BACKEND_API_BASE_URL=https://space-syntax-production.up.railway.app`를 넣으면
   라이브 백엔드로 프론트 확인 가능 (클라우드 세션엔 이 파일이 없을 수 있음 — 백엔드 변경은
   테스트로만 검증하고, 라이브 확인은 필요시 사람이 한다).

## 제품 방향 (기초 설계 요약)

**소비자 중심**: 판매자 중심(정보 나열)이 아니라, 사용자가 원하는 것을 먼저 요약해 보여주고
더 물으면 확장하는 인터페이스. "새 분석" 탭(자연어 에이전트 챗)이 이 방향의 핵심 실험 지점.

**LLM 답변 원칙**:
- 플랫폼이 가진 모든 정보를 고객 질문에 맞춰 **답 안에 자연스럽게 녹여서** 보여준다 (나열 금지).
- 플랫폼에 없는 정보는 일반 LLM 지식으로 대체.

**예시(examples) 설계 — 두 가지 사용자 의도**:
1. **골목 비교**: "신촌에서 카페 하려면 어떤 골목이 좋은지 비교해줘" — 지역+업종은 정했고,
   그 안에서 **어디가 좋은지**를 묻는다. 특정 주소를 여러 개 찍어 비교하는 게 아니다(그 주소가
   공실이 아닐 수 있어 무의미). **골목(길/segment) 단위로 비교**한다 — space syntax의
   integration/choice가 원래 segment 단위 값이라 이 방향과 정합. "이 골목은 유동인구 많다,
   20대가 많이 다닌다" 식으로 답한다. **미착수 — 설계만 있음, 아직 구현 안 됨.**
2. **단일 주소 평가**: "신촌 ○○로 12번지 카페 자리 어때?" — 특정 주소를 이미 점찍은 사람이
   그 주소가 그 업종에 좋은지 묻는다. **이건 지금 "새 분석" 챗이 이미 하는 것과 같은 흐름.**

**분석 프레임워크 — 인플로우(수익) / 아웃플로우(비용) 두 축**:
- 인플로우: 수요 규모, 소득 수준, 유동인구, 소비 여력 인구, 고객층(성별·연령 %), 경쟁 점포 수.
- 아웃플로우: 임차/구매 비용, 실거래가(평균 수준으로, 콕 집지 않게), **보증금·권리금은 데이터가
  없으므로 매물 정보(네이버 등) 링크로 연결**.
- **골목 단위가 목표.** 매출은 보통 동 단위로만 나오는데, 서울시 상권분석서비스가 2024년부터
  "표준단위구역" 단위로 제공(카드사 데이터, data.seoul.go.kr OA-15572) — 동보다 세밀해
  골목 단위에 가장 가까운 원 데이터. 이걸 적재하면 골목 단위 매출 추정이 가능해질 수 있음
  (조사만 됨, 적재 안 됨 — 큰 작업).
- 대안: 골목 단위 매출 데이터가 세상에 없다는 게 확인됐으므로, **동 단위 매출을 space syntax
  (integration/choice)로 골목마다 배분·추정**하는 것이 이 앱만의 차별점이 될 수 있음(아이디어,
  미착수).
