# 5초 룰을 넘기는 원인 — 측정 결과 (2026-07-29 새벽, 라이브 Railway)

> 결론부터: **"무거운 도구를 2단계로 미루면 된다"는 전제가 틀렸다.** 서술은 이미
> 2단계로 분리돼 있고(`/api/agent/ask?include_answer=false` → `/api/agent/answer`),
> 남은 시간은 전부 도구 자체에서 난다. 진짜 병목은 **캐시되지 않는 도로망·접근성
> 계산**이다.

## 무엇을 쟀나

라이브(`space-syntax-production.up.railway.app`)에 직접 요청해 측정했다.
스크립트는 `backend/tools/perf/`에 있다.

### 1. 후보 수는 병목이 아니다

`goals.py`의 주석은 "후보 1곳당 입지 분석이 통째로 한 번 돌기 때문에 응답
시간이 후보 수에 정비례한다"고 적고 있는데, 실제 기울기는 훨씬 완만하다.

| 요청 | 시간 |
|---|---|
| area-search 후보 1곳 | 9.4s |
| area-search 후보 2곳 | 10.0s |
| area-search 후보 3곳 | 11.8s |
| area-search 후보 5곳 | 13.7s |

**고정비 약 8.5초 + 후보당 약 1초.** 후보를 5곳에서 1곳으로 줄여도 9.4초라
5초 안에 못 들어온다. 후보 수를 줄이는 건 답이 아니다(추천 품질만 깎인다).

### 2. 같은 질의를 반복해도 빨라지지 않는다

| 요청 | 시간 |
|---|---|
| 연남동 5곳 1회차 | 13.8s |
| 연남동 5곳 2회차 | 13.8s |
| 연남동 5곳 3회차 | 12.7s |

탐색 반경은 800m(`search_radius_for`가 동 이름에 주는 값). **완전히 같은 입력을
세 번 보내도 전혀 빨라지지 않는다** — 매 요청마다 도로망을 새로 받아 그래프를
만들고 DepthmapX 적분을 다시 돌린다.

### 3. 그런데 그 계산은 이미 캐시가 있다 — 다른 경로에서만 쓴다

`/api/analyze`는 `analysis_cache`(격자 스냅 영구 캐시, Postgres)를 쓴다.

| 요청 | 시간 |
|---|---|
| analyze 1km 1회차 (cold) | 6.8s |
| analyze 1km 2회차 (warm) | **2.0s** |

같은 종류의 계산인데 캐시가 붙은 쪽은 **3.4배** 빠르다. `area_search`의
`_extract_spots`(goals.py:860)는 이 캐시를 통과하지 않는다.

### 4. 단일 지점 분석도 이미 5초를 넘는다

| 요청 | 시간 |
|---|---|
| site-score 1회 | 7.3s |
| site-score 재요청 | 5.5s |

그래서 **도구를 뒤로 미루는 방식으로는 어떤 조합도 5초 안에 못 들어온다.**
가장 가벼운 도구 하나가 이미 예산을 넘는다.

## 그래서 무엇을 할 수 있나

우선순위 순.

1. **`_extract_spots`를 `analysis_cache`에 태운다.** 고정비 8.5초의 대부분이
   여기다. 캐시는 이미 있고, 키가 격자에 스냅돼 "가까운/반복 클릭이 같은
   항목에 떨어지도록" 설계돼 있다(`analysis_cache.py`의 `snap_to_analysis_grid`
   주석). 잘 되면 반복 질의가 analyze처럼 2~3초대로 떨어진다.

   **주의(이래서 밤중에 손대지 않았다)**: 캐시 키에 `segment_limit`·반경·
   엔진·network_version이 들어간다. 키를 하나라도 어긋나게 잡으면 area_search가
   **다른 도로 집합에서 뽑은 후보**를 돌려주게 된다 — 응답 시간이 아니라
   "어디에 가게를 내라"는 추천이 조용히 바뀐다. 캐시 히트 시 후보 목록이
   미스일 때와 **완전히 동일한지**를 먼저 검증해야 한다(같은 좌표로 두 번
   호출해 후보 5곳의 osm_id·좌표·점수가 정확히 같은지).

2. **서울 주요 동을 미리 데워 둔다.** `tools/precompute_analysis_cache.py`가
   이미 격자를 도는 구조다. 1번을 하면 이게 그대로 area_search에도 듣는다.

3. 그래도 남으면 그때 응답 구조를 논의한다. 다만 위 측정대로라면 구조를
   바꿔도 도구 자체가 5초를 넘으므로, **5초 룰을 "첫 화면이 뜨기까지"로
   정의를 바꾸는 것**이 실제로는 더 정직한 선택일 수 있다. 지금도 분석과
   서술은 분리돼 있어 첫 화면은 도구가 끝나는 즉시 뜬다.

## 캐시를 붙이기 전에 찍어 둔 기준선

캐시 적용의 위험은 느려지는 게 아니라 **추천이 조용히 바뀌는 것**이다. 그걸
확인하려면 "지금 결과가 애초에 결정적인가"부터 알아야 한다 — 지금도 호출마다
흔들린다면 캐시 적용 후의 비교로는 캐시 버그와 원래 있던 비결정성을 구분할 수
없다.

`backend/tools/perf/qa_area_identity.py`로 4개 동네를 두 번씩 불러 후보 5곳의
osm_id·좌표·추천점수·판정·예상매출·감당가능월세를 비교했다.

```
[연남동]            반복 2회 동일  (11.6s / 9.1s)  후보 5곳
[성수동]            반복 2회 동일  ( 8.4s / 7.0s)  후보 5곳
[구로디지털단지역]  반복 2회 동일  ( 7.5s / 6.3s)  후보 5곳
[중계동]            반복 2회 동일  ( 6.6s / 5.4s)  후보 5곳
```

**지금 area_search는 결정적이다.** 그래서 캐시를 붙인 뒤 같은 스크립트를
`--baseline backend/tools/perf/area_search_baseline.json`으로 돌리면, 값이
하나라도 달라지는 순간 캐시 키가 어긋났다는 뜻이 된다.

```bash
# 캐시 적용 후
PYTHONUTF8=1 python backend/tools/perf/qa_area_identity.py     --baseline backend/tools/perf/area_search_baseline.json
```

기준선은 **도로망 데이터(network_version)가 그대로일 때만** 유효하다. 도로망을
다시 적재했다면 기준선도 `--save`로 다시 찍어야 한다.

### 시간에 대한 단서 하나

이 측정에서는 두 번째 호출이 조금 빨랐다(11.6→9.1초 등). 앞의 반복 측정
(13.8/13.8/12.7초)과 합쳐 보면, 이건 캐시가 생겨서가 아니라 부하에 따른
흔들림이다 — `/api/analyze`가 캐시를 탈 때 보이는 6.8→2.0초 같은 **계단**이
없다. 절대 수치는 부하에 따라 변하므로, 판단은 "반복 호출에서 계단이
보이는가"로 할 것.

## 재현

```bash
PYTHONUTF8=1 python backend/tools/perf/qa_area_profile.py    # 후보 수 vs 시간
PYTHONUTF8=1 python backend/tools/perf/qa_area_repeat.py     # 반복 질의 캐시 여부
PYTHONUTF8=1 python backend/tools/perf/qa_cache_contrast.py  # analyze(캐시) 대비
```

라이브를 그대로 때리므로 배포 중에는 숫자가 흔들린다. 각 스크립트는 읽기
요청만 보낸다.
